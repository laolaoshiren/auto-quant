# 协作作业手册（维护者用）

面向**维护者**（我）。贡献者该看的规则在 [`../CONTRIBUTING.md`](../CONTRIBUTING.md)，
发版流程在 [`RELEASING.md`](RELEASING.md)。

本文回答一个问题：**外面提了 PR / Issue，我按什么标准处理、什么情况下合、什么情况下退。**
本项目的特殊性是它会**下真实订单** —— 所以"能不能合"的标准不是"代码好不好看"，
而是"这个改动能不能让真钱出错"。

> ⚠️ **除了处理 PR，维护者还有一项长期职责：防屎山。**
> 这个项目现在**由自动化持续改动**（外部 agent 提 PR、我合并且自己也在改），
> 而自动化没有"项目品味"——它只会让代码越积越多。
>
> 定期审计（屎山特征 + 安全）与**教训沉淀**见 [`MAINTENANCE.md`](MAINTENANCE.md)。
> **每次审计后往那里的「教训库」加条目** —— 不写下来的教训等于没学到。

---

## 0. 一条红线（每次处理前先记起）

> **禁止在同一分钟内连续调用 `gh`，禁止把 `gh` 放进循环。**
>
> 2026-09-25 真实事故：agent 在几分钟里连续创建+合并 6 个 PR、每个都跑
> `gh pr checks` 轮询，账号被 GitHub **suspend**。原话：
> 「你以后迭代别老纠结 GITHUB 了……你保证本地完整没问题就行了。」
>
> 所以：
> - **看 CI 结果用网页**，不要 `gh pr checks` 轮询。
> - **一次只处理一个 PR**，处理完再做下一个。
> - **攒批**：一个迭代 = 一个 PR。多个 commit 可以，多个 PR 不行。
> - 失败就停下报告，不要写 `for` 循环重试十几次。

---

## 1. 每天一次的处理节奏

**不要被动等通知。** 一天开一次 PR / Issue 列表，集中处理：

```
① 打开 https://github.com/<owner>/<repo>/pulls  →  看到几个待处理
② 逐个看：CI 结果（页面上就有）→ diff → 判断
③ 处理完一个再看下一个（不在同一次里批量调用 API）
```

⚠️ **不要给每个 PR 都写长评论。** 这个仓库的读者是 AI 与我自己 ——
一条精准的评论（"第 42 行会绕过风控"）比一段格式化的客套话有用得多。

---

## 2. 判断一个 PR 能不能合：五道闸门

按顺序过。**任何一道不过就退，不要"先合了再修"。**

### 闸门 ①：CI 绿吗

`ci.yml` 会在 PR 页面给出四条结果。**任一红 → 退。**

```
类型检查 · Lint · 测试 · 构建 · 密钥扫描
```

⚠️ **例外**：若红的是**测试本身写错了**（fixture 不满足前置条件、断言的是实现算出来的值
而非观测到的真实值），而不是被测行为有问题 —— 那是可以合的，但**必须在评论里说清
"是哪条测试错了、为什么"**，并且改测试的提交要单独一个。

### 闸门 ②：有没有碰这五个「不可违反的不变量」

见 [`AGENTS.md`](AGENTS.md#2-改动规则不可违反的不变量)。逐条问：

| 不变量 | 怎么快速查 |
| --- | --- |
| 风控引擎是通往订单的唯一路径 | diff 里有没有新的 `placeOrder()` 调用点 |
| 每一张订单都要被记录（含被拒绝的）| 有没有新增"提前 return 而不 `recordOrder`"的分支 |
| 每一笔平仓都要入账（三层保障）| 有没有放宽 `orders.exchangeOrderIds()` 的归属闸门 |
| 模型的输出是不可信输入 | 有没有放宽 `parser.ts` 的**语义**校验（字段别名可以，语义不行）|
| 净 = 毛 − 手续费 − 资金费 | 有没有在 `trades.insert()` 之外自己算金额 |

**碰了任何一条 → 逐行读那段 diff，不要只看 CI 结果。**

### 闸门 ③：有没有碰「涉及真实资金的改动」

`labeler.yml` 会把这类 PR 打上 `risk-engine` / `trading-path` / `accounting` 标签。
**带这些标签的 PR 需要更高一级的验证**（见 `CONTRIBUTING.md` 的阶梯）：

```
单元的 → 脚本化模拟（npm run sim）→ 真实模型+模拟交易所 → … → 实盘
```

⚠️ **不接受"我读了觉得对"**。要么 PR 里说明了验证到哪一级，要么我本地补跑：

```powershell
npm run typecheck; npm test      # 最低门槛
npm run sim                      # 接缝：保护单、记账、权益曲线
```

### 闸门 ④：有没有混进站点专属信息或凭据

```
❌ 主机名、域名、IP、服务器路径、凭据
✅ 占位符：my-server / https://quant.example.com / /srv/<应用目录>
```

`ci.yml` 的密钥扫描只抓常见字面量，抓不到"一个看起来无害的真实域名"。
**这一条要靠眼睛。**

### 闸门 ⑤：提交信息合规吗

`AGENTS.md` §5.5：**只写一行标题，不写正文。**

```
✅ fix(agent): 熔断锁死时不再每 15 分钟唤醒一次
❌ 上面那行 + 四十行"起因 / 决定 / 效果 / 验证 / 实测数字"
```

⚠️ **不合规但不影响正确性** → 用 **squash 合并**（合并时写一个合规的标题），
不要为了一行提交信息打回去让人重做。

## 3. 合并方式：一律 squash

```
gh pr merge <n> --squash --delete-branch
```

理由：
- 历史干净（一个 PR = 一个提交），与本仓库「一次迭代 = 一个 PR」一致；
- 提交信息在 squash 时由我写，可以直接满足 §5.5 的一行要求；
- ⚠️ 本仓库**不允许 merge commit**（`main` 的历史是线性的）。

⚠️ `gh pr merge --squash` **成功时可能没有输出** —— 用一次
`gh pr view <n> --json state,mergedAt` 核实（**单次调用，不放循环**）。

## 4. 处理 Issue

| 类型 | 动作 |
| --- | --- |
| **交易事故**（带 `incident` 标签）| **最高优先级。** 先看是不是真在亏钱，再定位；不要先回复 |
| 有复现步骤的 bug | 直接修 → 修的时候**先写一个能复现的用例**（`AGENTS.md` §3.5）|
| 功能请求 | 判断是否与本次大更新方向一致 → 打 `enhancement` 或说明为什么不收 |
| 重复 / 无效 | 打 `duplicate` / `invalid` 并一句话说明 |

⚠️ **Issue 不是待办清单。** 我会把它们转成**分支上的实际工作**，
而不是留在那里当作"已记录"。原因是这个仓库的读法：`AGENTS.md` 说了
「注释与文档里的记录比 issue 列表有用得多」—— 真正要留下的信息写进代码注释或 `docs/`。

## 5. 我自己的改动走哪条路

⚠️ **不经过 PR。** 我自己的迭代是：

```
改代码 → npm run typecheck / lint / test（+ build）→ git commit（一行标题）
→ pwsh -File scripts/deploy.ps1 → 回读线上 build-info.json 的 commitShort == 本地 HEAD
```

理由见 `AGENTS.md` §4.6：**没有部署的迭代等于没做完**，而部署走 scp/ssh，不经过 GitHub。
所以直接推 `main` 是允许的（`ci.yml` 会在 push 后跑一次，但**不阻断**）。

⚠️ 这不等于可以跳过闸门 ①②③ —— 只是**没有第二个 reviewer**。
所以对自己要更严：**碰了风控或账目算术的改动必须加测试**，而不是"我读过一遍"。

## 6. 从别人的 PR 里学什么

外部协作的价值不只是"多几个人写代码"，还有**他们的审计视角**。真实例子（2026-10-13）：

一个只读审计（不是我提的）发现了**两条我修漏的规则丢失路径**，其中一条**每轮必触发**：

```
① 我修了 splitMarketContext 的切片丢规则段
② 又修了 headOfMarket 的 break 丢规则段
→ 但审计指出：修①把规则段搬进了 shared，而 shared 正是 headOfMarket 眼里的"概览"
   于是 overviewCap 腰斩了它 —— 【两个各自正确的修复合起来失效】
```

**所以：收到"你这里不对"的 PR / Issue 时，先假设对方是对的，去复现。**
不要先解释"我是这么想的"——这个仓库已经吃过好几次"我以为搜过了"的亏。
