## 关键判断记录

### ① 为什么 `minScore=0` 而不是"调低到 0.3"

Jev 的 score 是 **0–4 量表归一化**后的值（`score / (criteria.length - 1)`）。
实测分布：**最高 0.64、最低 0.22** —— 它不会给出 0.9 这种高分。

两个选择：
```
A. 把门槛调到 0.35 → 勉强保留一部分，但门槛是个魔数，随行情漂移
B. 门槛设 0，只按排名取前 N → 语义变成"Jev 挑出相对最好的 N 个"
```

**选 B**，理由：
- 我们要的本来就是"**在 19 个里挑出最值得深看的 6 个**"，而不是"Jev 认为值得的才看"
- 绝对分数会随市场整体行情漂移（普跌时全都低分），用固定门槛等于"行情差的时候团队就停摆"
- **B 保证了"永远有 6 个进 LLM"** —— 这是我们对"不能因为实验功能掐死团队"的具体落实

### ② 这次发现说明什么

**这就是用户要求"定期观察 10 小时"的价值。** 如果只看"Jev 调用成功了"，会得出"功能正常"的结论；
而实际上它把 19 个标的砍到 1 个 —— 团队几乎停摆，且**不会报错、不会告警**，只会"决策变少"。
这正是本仓库反复记录的那类失败：**静默变差，而不是报错。**

## 09:00 更新 · 两个重大发现与修复

### 🔴 发现 1：Jev 静默把 19 个标的筛到 1 个

```

## 12:00 · 🔴 修了一个会让采样永久断掉的 bug

### 症状

### 根因：环形缓冲把「保留行」和「筛除行」冲散了

日志原来是三行：
```
132633  [Jev] 20 个标的 → 保留 6 个 · 最高 0.61 · 耗时 1482ms
132634  [Jev] 保留：QUSDT AGTUSDT …

```

而采集脚本靠"保留行 + 下一行筛除行"**配对**。`runtime_logs` 是环形缓冲
（500 条 ≈ 100 分钟），只要中间被别的日志挤掉一行，那一轮就**永久采不到**。

```

132635（筛除行）成了孤儿
⇒ 配对失败 ⇒ 那一轮永远采不到
```

```
[Jev] 保留：QUSDT AGTUSDT … | 筛除：EPICUSDT(0.50) GTCUSDT(0.49) …
[Jev] 20 个标的 → 保留 6 个 · 最高 0.61 · 耗时 1482ms
```

**⇒ 一行就是一轮的完整判定，不存在"被冲散"的可能。**

采集脚本同步改成两种格式都认（旧三行 + 新两行），保证存量样本还能用。

## 12:20 · 补齐最后一个契约盲区：Jev 端点探针

### 发现的缺口

models.shape / models.metadata / models.ladderIds / quotas.shape
```
**但没有探 Jev 自己的 `/v1/systemone`。**

### 为什么那是最危险的一个

```
/v1/systemone 是【非标准端点】（TypeSafe 自己的 Decisions API，不是 OpenAI 兼容协议）
      ↓ magpie 一天多版，任何"顺手重构路由"都可能把它改掉
      ↓ 而它一坏：
           Jev 初筛 → 降级到"不筛" → 每轮重新分析全部 20 个标的
           耗时从 110s 回到 300s+
           而且【不会报任何错】
```

**这正是本项目反复记录的那类失败：静默变差，不是报错。**

### 已补上（`gatewayContract.ts` 探针 5）

| 项 | 内容 |
|---|---|
| 何时探 | **只在 `AQ_JEV_PREFILTER=on` 时**（没开时那个端点与我们无关，多打请求违背本层纪律） |
| 探什么 | 发一个 `noul` 问句，只验 `answers.<任意键>.type` 是字符串 |
| 成本 | 一次调用 `input≈268 / output≈20` token ⇒ 按 Jev 定价 **≈ 0.00001 美分** |
| 判据 | `warn`（不是 error）—— Jev 坏了会降级，不影响交易 |
| 提示 | 「Jev 初筛会降级为'不筛'（仍能工作，但每轮会多花 2-3 倍时间）」 |
