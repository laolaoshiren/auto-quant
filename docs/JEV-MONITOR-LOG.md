## 关键判断记录

### ① 为什么 `minScore=0` 而不是"调低到 0.3"

Jev 的 score 是 **0–4 量表归一化**后的值（`score / (criteria.length - 1)`）。
实测分布：**最高 0.64、最低 0.22** —— 它不会给出 0.9 这种高分。

两个选择：
```
A. 把门槛调到 0.35 → 勉强保留一部分，但门槛是个魔数，随行情漂移
B. 门槛设 0，只按排名取前 N → 语义变成"Jev 挑出相对最好的 N 个"
```

**选 B**，理由：
- 我们要的本来就是"**在 19 个里挑出最值得深看的 6 个**"，而不是"Jev 认为值得的才看"
- 绝对分数会随市场整体行情漂移（普跌时全都低分），用固定门槛等于"行情差的时候团队就停摆"
- **B 保证了"永远有 6 个进 LLM"** —— 这是我们对"不能因为实验功能掐死团队"的具体落实

### ② 这次发现说明什么

**这就是用户要求"定期观察 10 小时"的价值。** 如果只看"Jev 调用成功了"，会得出"功能正常"的结论；
而实际上它把 19 个标的砍到 1 个 —— 团队几乎停摆，且**不会报错、不会告警**，只会"决策变少"。
这正是本仓库反复记录的那类失败：**静默变差，而不是报错。**

## 09:00 更新 · 两个重大发现与修复

## 12:00 · 🔴 修了一个会让采样永久断掉的 bug

### 症状

### 根因：环形缓冲把「保留行」和「筛除行」冲散了

日志原来是三行：

```

132635（筛除行）成了孤儿
⇒ 配对失败 ⇒ 那一轮永远采不到
```

```
[Jev] 保留：QUSDT AGTUSDT … | 筛除：EPICUSDT(0.50) GTCUSDT(0.49) …
[Jev] 20 个标的 → 保留 6 个 · 最高 0.61 · 耗时 1482ms
```

**⇒ 一行就是一轮的完整判定，不存在"被冲散"的可能。**

采集脚本同步改成两种格式都认（旧三行 + 新两行），保证存量样本还能用。

## 12:50 · 🎯 用「窗口判断」根治追高问题（实测有效）

Jev 只看一眼摘要，**分不清这两者 —— 而分不清是因为信息不足，不是能力不足。**

```diff
  const jevInputs = allSlices.map((s) => ({

-   digest: compactSeriesLines(s.text, 5),

current_price=0.1392  current_ema20=0.1350
24h_change=+56.17%
...
```

**⚠️ 这是"给 Jev 更多信息"，不是"让它算"** —— TypeSafe 官方明确说 Jev 的弱点是
算术与计数，而"算好再喂"正是规避它的正确姿势。

## 12:55 · 排查一批对账警告（结论：防护正常工作，不是新问题）

### 现象

`runtime_logs` 里突然出现 **168 条**「对账算出的成交量与本地记录差得太远」：

```
03:00 之前：0 条
03:00 之后：168 条   ← 全部集中在 03:56 这一分钟
```

**⇒ 那不是"持续在出问题"，而是那次重启的启动对账一次性把积压的全打出来了。**

### 消息本身说明了机制

```
对账算出的成交量（60）与本地记录（18）差得太远
—— 已保留本地数量与本地金额（重建那个腿的边界是错的，
   它的金额可能是多个回合的合计）。
   这通常意味着成交历史的窗口起点落在持仓中间，重建把开/平判反了。
```

**⇒ 系统识别出"重算是错的"，于是保留本地数据 —— 这正是设计的行为（不让错误数据污染账本）。**

### 倍数规律证实了成因

```
60 / 18 = 3.3        176.3 / 88.4 = 2.0
403 / 120 = 3.4      296.2 / 148.3 = 2.0
399 / 159 = 2.5      36.4 / 18.2 = 2.0
```
**⇒ 重算值普遍是本地值的 2-3.4 倍，正是"重建把多个回合合并了"的特征。**

而根因写在消息里：**「成交历史的窗口起点落在持仓中间」** ——
`getUserTrades(symbol, 500)` 只取最近 500 笔，窗口起点可能落在一个持仓中间，
于是重建误把"平仓"当成"开仓"，整条序列错位。

### 账本正确性验证（这是关键）

```
平台记录  0.6472 USDT
交易所流水 0.0000 USDT
差额      0.6472
【本机器人成交 0.6472】   ← 与"平台记录"完全一致
```

**⇒ 平台记录 == 本机器人成交（0.6472 = 0.6472），账是对的。**
**⇒ 那个"交易所流水 0.0000"是**全账户**口径（含其他机器人），不是我们的账错。**

自检也确认：
```
[自检/ai] 持仓保护完整｜当前开仓 1 个，全部有止损价或止损单｜下一步：无需处理
```

### 结论

| 项 | 判断 |
|---|---|
| 是否新问题 | **否** —— 是启动对账把积压的警告一次性输出 |
| 是否与 Jev 有关 | **否** —— 对账路径与 Jev 完全无关 |
| 账本是否被污染 | **否** —— 系统保留了本地数据（这正是防护的目的） |
| 需要修吗 | **不需要** —— 这是已知边界的正确表现 |
| 需要改进吗 | 🟡 **可以**：168 条一次性输出会淹没有效日志。建议聚合成一条（"XX 个标的重建边界异常，已全部保留本地数据"） |

**⇒ 记为"可选改进"，不在本次实验范围内。**
