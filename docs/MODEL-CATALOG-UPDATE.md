# 模型档案与更新步骤

> 需求原话：
> > 「每个智能体根据工作内容来制定用什么模型……不同模型智商、速度、上下文等等不同，
> >  具体做什么你来安排（当然你得先真实去查资料了解清楚，给程序建立一套档案，
> >  **还有更新的程序步骤**，方便以后渠道更新了新模型，你也能更新相应的模型参数）」
>
> 本文是那份「更新步骤」。**先读第 1 节**（它决定你该不该手动做任何事）。

---

## 1. 结论先行：大多数情况下**你不需要手动更新**

系统**自己会发现**上游模型变化。线上实测（2026-10-15）：

```
07:46:52  models.dev 快照已装载：2221 个叶子名
09:14:11  models.dev 目录已更新            ← 检测到上游变化，自动更新
09:47:17  models.dev 目录已更新            ← 再次更新
07:50:20  models.dev 目录没有变化（304）   ← 没变化就不动（省流量）
```

```
渠道上新模型  →  系统自动发现  →  自动判断档位  →  自动进入候选链
                 ↑ 这是常态路径，不需要人介入
```

**只有三种情况需要手动**（见第 4 节）：
```
① 新模型**分档错了**（它被放进一个不合适的档位）
② 新模型的**输出契约服从性**差（它进了候选链但总解析失败）
③ 某个渠道**整体挂了**，而候选链里没有可用的替代
```

## 2. 档案在哪里（四个文件，各管一件事）

| 文件 | 管什么 | 什么时候改它 |
| --- | --- | --- |
| `packages/server/src/llm/modelCatalog.ts` | **能力档位定义**（`T0_code` / `T1_fast` / `T2_mid` / `T3_deep`）+ `MODEL_PROFILES` | 档位的**判据**变了（例如"实测 3 秒那一档"的边界变了） |
| `packages/server/src/llm/modelDiscovery.ts` | **自动发现与自动分档**（`inferTier` / `buildCatalog` / `mergeDiscovered`） | 分档规则要改（例如新指标要参与判断） |
| `packages/server/src/trader/routedModel.ts` | **角色 → 档位**（`ROLE_TIERS`）+ **候选链**（`ROLE_GROUP_LADDERS` / `TIER_GROUP_LADDERS`） | 某个角色该用更聪明/更快的模型，或候选链要加减 |
| `packages/server/src/llm/modelsDev.ts` | **第三个数据源**（models.dev 的 2221 个叶子名，补 cost / 知识截止 / tool_call） | 上游字段名变了 |

### 2.1 三个数据源各缺什么（决定了为什么需要三个）

```
GET /v1/models          有 context / max_output / reasoning / 思考等级
                        ✗ 没有 cost，✗ 没有知识截止，✗ 没有 tool_call

plugin-providers.json   有 free / rate / released / fast
                        ✗ 是网关自己的配置，模型一换就与上游脱节

models.dev              有 cost / 知识截止 / tool_call（2221 个叶子名）
                        ✗ 只有元数据，没有"这个渠道现在能不能用"
```

⚠️ **不要把三个源的同一个字段混用** —— 它们的口径不同（实测踩过：`cost` 的键是
`input` / `output` / `cache_read` / `cache_write`，写成 `cache` 会静默拿到 `undefined`
并把缓存价记成 0）。

## 3. 档位的判据（**不是"模型名"，是"这个角色需要多聪明"**）

```
T0_code    不用 LLM，纯代码算（指标、风控限额、下单、对账）
T1_fast    小快模型：字段映射、打标、摘要、情绪打分。实测 ≈1.5s 那一档
T2_mid     中档：单源分析、记忆反思、教训提炼。实测 4–5s 那一档
T3_deep    强推理：辩论、组合决策、风控裁决、异常归因。实测 3–7s 那一档
```

依据：Anthropic 的多 agent 工程结论 —— **多 agent 约 15× chat 的 token**，
所以「把不需要智商的工作压到低档」是这套架构能不能长期跑下去的前提。

### 3.1 候选链（ladder）—— 「首选挂了就往下降级，永远有得用」

```
ROLE_GROUP_LADDERS    按角色定（例如 judge → 某个强推理组）
TIER_GROUP_LADDERS    按档位兜底（例如 T1_fast → group/team-grunt）
```

**为什么必须有链**：实测额度事实 —— `workbuddy-ai` 只剩 3.13/350 credits、
`cline` 只剩 $0.50。**首选不能是额度最少的那类**，且链里必须包含免费档。

⚠️ 单组一次 5xx 会让整档不可用（实测踩到），所以链里**至少两个不同组**。

## 4. 需要手动介入的三种情况（操作步骤）

### 情况① 新模型分档错了

```bash
# 1. 看它现在被分到哪一档（线上）
#    日志里搜它的名字，或查发现结果
grep -a "<模型名>" <数据目录>/server.log | tail -5

# 2. 确认"错"的证据 —— ⚠️ 不要凭感觉，要有实测
#    分档错的表现是：它在 T1 却总解析失败，或它在 T3 却明显更快更好

# 3. 改分档规则（不是改单个模型！）
#    编辑 packages/server/src/llm/modelDiscovery.ts 的 inferTier()
#    ⚠️ 改规则会【影响所有模型】—— 所以必须跑：
npm run typecheck && npm test

# 4. 若只是"这个模型该特殊对待"，改 MODEL_PROFILES（modelCatalog.ts）
#    并在注释里写清实测依据（这是本仓库的硬要求）
```

### 情况② 新模型输出契约服从性差

```
表现：它进了候选链，但总是"没有找到 JSON 对象"
⇒ 这不是分档问题，是【这个模型不适合那个角色的输出契约】
⇒ 把它从那个角色的 ROLE_GROUP_LADDERS 里移出（或降档到 T1 做体力活）
```

### 情况③ 某渠道整体挂了

```
表现：连续 5xx，整档不可用
⇒ 在 ROLE_GROUP_LADDERS / TIER_GROUP_LADDERS 里补一个替代组
⇒ 或在网关侧调整（更根本）
```

## 5. 改完必须验证（**这是本仓库的纪律，不是建议**）

```bash
npm run typecheck     # 必须 0
npm run lint          # 必须 0
npm test              # 必须全绿
pwsh -File scripts/deploy.ps1
# 回读线上版本，确认 commitShort == 本地 HEAD
```

**并且要看线上日志确认自动发现仍然在工作**：

```bash
grep -aE "models.dev|目录已更新|快照已装载" <数据目录>/server.log | tail -5
```

判据（不是"看起来对"）：
```
· 「快照已装载：N 个叶子名」—— N 应当与上游一致（实测 2221）
· 「目录已更新」/「目录没有变化（304）」—— 两者都正常（后者是省流）
· 若长时间只有"没有变化"而没有"已装载" → 说明装载环节坏了
```

## 6. 我已知的缺口（诚实列出）

⚠️ **写这一节时我犯过一次错**：我第一版写"`inferTier` 没有守卫测试"，
而实测它**有 26 条测试**（`modelDiscovery.test.ts`，含 6 条 `inferTier` 断言）。
**我没查就下了结论。** 下面是查过之后的真实情况。

### 6.1 覆盖情况（实测）

```
packages/server/src/llm/ 下共 18 个测试文件、239 条：
  modelsDev.test.ts        43 条   ← 第三个数据源的解析（含 cost 键名、limit 嵌套）
  modelDiscovery.test.ts   26 条   ← inferTier 分档 + buildCatalog
  modelRouter.test.ts      36 条   ← 路由与降级链
  llm.test.ts              47 条
  modelCatalog.test.ts      6 条
  （其余 13 个文件共 81 条）
```

⇒ **"自动分档"与"字段口径"都有测试**，这一层是扎实的。

### 6.2 真正的缺口

```
① 「快照装载 + 触发目录刷新」的【编排层】没有测试
   那是 `manager.ts` 里产生这两条日志的地方：
     models.dev 快照已装载：N 个叶子名
     models.dev 目录已更新 / 目录没有变化（304）
   而 modelsDev.test.ts 只覆盖了 modelsDev.ts 内部（含"重启后能装载"一条）。
   ⇒ 缺口是"编排"：谁在什么时候调它、装载失败怎么办、刷新失败会不会拖垮启动。
      这些在 §5 里我让用户去查日志 —— 而那条路径本身没有守卫。

② 手续费/资金费的口径差未解决（账本与交易所残差 0.6967 的主要来源）
   —— 与模型档案无关，但同属"账目可被信任"这个主题。

③ 三个数据源的【交叉一致性】没有测试
   各自解析正确 ≠ 合并后正确。`mergeDiscovered` 有 3 个生产调用点，
   而"同一个模型在三个源里字段冲突时以谁为准"这件事，我没找到测试。
```
