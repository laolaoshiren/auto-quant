# 裁决官输出被截断 → 整轮决策丢失（2026-10-15 定位并修复）

> 这是本轮最有价值的发现：**一个"看起来是判断、实际是故障"的失败**。

---

## 1. 症状

`#11` 团队模式有**空决策轮**（`decisions_json = []`），界面上显示成
「结论：空仓（模型没有给出任何决策）」—— 读起来像"团队判断不做"。

而 `raw_response` 有 **13,000–16,000 字**。查进去：

```
<decision>
[]
</decision>
```

**裁决官输出了空数组**。而同一轮的 `<team>` 块里写着（原文）：

```
⚠️ 裁决里的 JSON 解析失败（可能被截断）—— 本轮按"不行动"处理。片段：[
  {"symbol":"ZEREBROUSDT","action":"skip","setup_score":30,"setup_score_basis":"D=+3.42%…

attention: 裁决输出不可解析，导致本轮决策链路空转；
           需排查裁决角色的输出格式/预算截断问题
```

⇒ **它本来给出了一整份决策数组，但被从末尾砍断，解析失败，于是整轮决策消失。**

---

## 2. 机制（数据支撑）

`ROLE_MAX_TOKENS.judge = 8192`。而实测 judge 的输出长度
（全历史 59 个可测量轮次，从 `<team>` 块的"完整 N 字"抓）：

```
p10=4,468 · p50=5,844 · p90=9,921 · max=12,111
超过 8192 的: 14 / 59（23.7%）
```

**超限率与候选数强相关**（机制清楚 —— 候选越多，数组越长）：

| 候选数 | 轮数 | judge 平均长度 | 超 8192 的轮数 | 超限率 |
| --- | --- | --- | --- | --- |
| ≤6 | 34 | 5,804 | 3 | 8.8% |
| 7–12 | 6 | 5,551 | 0 | 0.0% |
| 13–18 | 11 | 7,897 | 6 | **54.5%** |
| >18 | 8 | 8,897 | 5 | **62.5%** |

空决策轮里 judge 的输出长度实测：**5,042 / 5,265 / 6,756 / 10,854 / 11,847 字**。

---

## 3. 为什么现在才暴露（两个因素叠加）

```
① 候选数变多：早期 ≤6，后来 13–20
② 2026-10-15 给 judge 补的提示词要求
   「每条决策都要给 reasoning：写"风险较高"是没用的；
     写"该标的在我历史上 11 笔净约 -0.005、胜率 36%，属磨损标的"才有用」
   ⇒ 每条 reasoning 变长 ⇒ 数组整体变长
```

⚠️ 而提示词里**早就有**一条针对截断的教训：
> 「先输出 JSON 数组，再写理由…实测教训：第一版让模型"先写理由再给数组"，
>  而输出预算用尽时从末尾砍 —— 于是被砍掉的正是那个数组」

**它防的是"理由写在数组前面"，防不住"数组里每条都很长"。**
这是一个真实的盲区：修了一个方向的截断，另一个方向还在。

---

## 4. 修法（两层，缺一不可）

### ① 预算 `8192 → 16384`

```
算术：16384 token / 97.6 token/秒（实测撞上限吞吐）≈ 168 秒
T3_deep 超时线 = 360 秒  ⇒ 余量 2 倍以上 ✅
实测 max = 12,111 字 ⇒ 16384 留 35% 余量
```

### ② 提示词加"数组每条要短"的纪律

```
- reasoning 一句话，不超过 60 字，只写最硬的那条依据
- setup_score_basis 同样一句话
- 分析过程不要写进数组；需要长论证时写在数组【之后】
- 20 个候选 × 每条 60 字 ≈ 1,200 字，那是安全的
```

**为什么两层都要**：候选数还会涨，而预算是有限的 ——
只加预算等于把问题推后；只改提示词则遇到"确实需要长输出"的那一轮仍会丢。

---

## 5. ⚠️ 修的过程中发现一条**自相矛盾的守卫**

`routedModel.test.ts` 里那条测试，注释自己说：

> 原来的断言是 `budget <= 2048`…而写死 2048 的断言就假失败了
> **真正的约束不是"预算 ≤ 某数字"，而是：
>  最坏耗时（预算 × 实测吞吐） < 该角色的超时线**

而紧接着**它对 judge 写的正是"写死 8192"** —— 同一种错，只是换了个数字。

**并且那个数字已经过期**：T3 超时线在 2026-10-13 从 180 秒提到了 **360 秒**
（原因：实测裁决官每轮都被切断、20 个候选只评了前 5 个），
而 8192 是那次调整之前的遗留值。

⇒ 已改成用**它自己声明的判据**（最坏耗时 < T3 超时线），
并另加一条独立边界（预算不能低于实测最大值 12,111 字的量级）。

## 6. 验证方式

```
① 单元层：routedModel.test.ts 的预算-超时协调测试（已改，全绿）
② 线上层（部署后观察）：
   判据 = 空决策轮里"含『解析失败』"的条数应当归零
   基线：10-15 的 27 轮里 3 条
   ⚠️ 需要足够样本（本仓库纪律：≥30 轮才能与噪声区分）
```

## 7. 一条更普遍的教训

这个失败**在界面上看起来是一个判断**（"本轮不做"），而在日志里也只是一行
「按不行动处理」。**如果不去看 `<decision>` 块的真实内容，永远发现不了它。**

⇒ 与仓库里那条既有纪律一致：**"一个说错话的错误信息比没有信息更糟"** ——
这里的变体是：**一个把故障说成判断的界面，比一个报错的界面更危险。**
