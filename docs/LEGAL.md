## 1. 第三方依赖许可证 【可技术确证】

### 结论：干净，无 copyleft

运行时会打进 Docker 镜像的依赖共 **145 个**，许可证分布：

| 许可证 | 包数量 | 义务 |
| --- | --- | --- |
| MIT | 107 | 保留版权声明与许可证文本 |
| ISC | 24 | 同上 |
| BlueOak-1.0.0 | 7 | 同上 |
| BSD-3-Clause | 5 | 同上 |
| Apache-2.0 | 1 | 同上；若包内有 `NOTICE` 还需一并保留 |
| MIT AND ISC | 1 | 同上 |

**没有任何 GPL / AGPL / SSPL / BUSL / Commons Clause 依赖**，也没有许可证未知的依赖。

### 这意味着什么

1. **本项目的许可证选择不受任何约束。** 可以自由选择
   MIT、Apache-2.0、AGPL 或任何其他协议 —— 不存在"被某个依赖传染"的问题。
2. **唯一的义务是署名。** 再分发（包括分发 Docker 镜像）时必须保留各依赖的版权声明与
   许可证文本。这一条已经通过 [`THIRD-PARTY-NOTICES.md`](../THIRD-PARTY-NOTICES.md)
   履行；各依赖的完整许可证文本也随包一起存在于镜像内的 `node_modules/<包名>/LICENSE`。
3. **已自动化。** `scripts/generate-notices.mjs` 在生成清单时会**拒绝** copyleft 与
   未知许可证的依赖，CI 每次都会跑。所以将来有人（或 AI 代理）加进一个 AGPL 依赖，
   会在合并前就被拦下，而不是在分发之后才发现。

> 为什么这条检查是失败的而不是警告的：许可证冲突一旦以错误的方式分发过，
> 就不再是"改一行配置"能解决的问题。它必须在引入依赖的那一刻暴露。

## 2. 本项目自己的许可证 【需专业意见】

本项目采用 **[Apache License 2.0](../LICENSE)**（自 v0.1.1 起；此前为专有软件）。

### 将来开源时的选项

| 协议 | 别人可以商用吗 | 必须回馈源码吗 | 特点 |
| --- | --- | --- | --- |
| **MIT** | 可以 | 不需要 | 最简单、最通用。**没有专利授权条款** |
| **Apache-2.0** | 可以 | 不需要 | 与 MIT 接近，但**含明确的专利授权**与商标条款 |
| **AGPL-3.0** | 可以 | **需要**（含"通过网络提供服务"的情形） | 防止别人拿去做闭源 SaaS。但很多公司**禁止**使用 AGPL 依赖 |
| **BSL 1.1** | 有限制 | 到期后转为开源 | 源码可见但限制商用，N 年后自动转为宽松协议 |

### 我的建议：**Apache-2.0**

理由：

1. **含专利授权。** MIT 没有。对一个会被别人拿去改、再分发的项目，
   专利授权条款能保护你和使用者双方 —— 这是 MIT 与 Apache-2.0 之间唯一实质性的差别。
2. **对使用者友好。** 这个项目的价值不在于代码本身，而在于策略与运行方式。
   用宽松协议能让更多人用起来、报 bug、贡献改进。
3. **AGPL 会显著缩小受众。** 很多公司的政策是"禁止引入 AGPL 依赖"。如果你的目标是
   让更多人使用，AGPL 会适得其反。只有当你明确想阻止别人拿它做闭源商业服务时，
   AGPL 才是正确选择。

**但这取决于你的目标**，需要你决定：

- 想让尽可能多的人用 → **Apache-2.0**
- 想防止别人拿去做付费服务 → **AGPL-3.0**
- 想先源码可见、几年后再完全开源 → **BSL 1.1**

> 无论选哪个，**在转换之前请让律师过一遍**，特别是如果届时已经有外部贡献者 ——
> 那时可能需要贡献者许可协议（CLA）才能变更整体授权。

### 一个容易忽略的点：外部贡献

一旦有人向公开仓库提交了代码，**你就不能单方面改变整个项目的许可证**了 ——
那部分代码的版权属于贡献者。如果预见到将来可能需要换协议，要么现在就用 CLA，
要么在 CONTRIBUTING 里写明"提交即表示同意按当前协议授权"。当前的
[CONTRIBUTING.md](../CONTRIBUTING.md) **没有**这一条。

## 3. 交易所条款 【需专业意见】

### 一条我们**实际观测到**的证据

本项目的 CI 在 GitHub Actions 上运行时，币安返回了这样一条错误：

```
Binance 0: Service unavailable from a restricted location according to
'b. Eligibility' in https://www.binance.com/en/terms.
Please contact customer service if you believe you received this message in error.
```

这不是推测，是本项目自己的构建日志。它说明：

1. **币安在 API 层面强制地理资格**，不只是网站访问限制。
2. 被拒的原因写在服务条款的 **"b. Eligibility"** 一节。
3. GitHub Actions 的运行节点（美国数据中心 IP）**不在**允许范围内。

**你自己的服务器是可以的**（本项目已在该服务器上完成过真实下单验证），
但这说明**用户所在的位置会直接决定这个软件能不能用**。

### 需要向律师确认的问题

- 在一个可访问的司法辖区**运行**本软件，是否完全符合交易所条款？（倾向于是，但需确认）
- **分发**本软件是否会被视为帮助受限地区的用户规避交易所的地理限制？
  （这是一个真实的风险点，尤其如果文档里教人怎么绕过）
- 交易所条款中关于**自动化交易**的具体限制是什么？是否有频率、策略类型、
  或"不得使用自动化手段"之类的条款？
- 如果将来提供**托管服务**（别人用你的实例交易他们自己的账户），
  这是否需要交易所的额外授权？

### 我建议采取的做法

1. **在 README 与文档中明确写出：使用者有责任确认自己所在辖区可以使用目标交易所。**
   这不是免责套话 —— 它把"用户自己违反条款"与"项目教人违反条款"区分开。
2. **不要提供任何绕过地理限制的功能或指引。** 本项目目前没有，将来也不要加。
3. 保留这条 CI 日志作为证据：本项目**没有**试图规避限制，遇到限制时是正常失败的。

## 4. 金融监管 【需专业意见】

这一块风险最高，也最依赖具体辖区，**必须问律师**。

### 目前的状态：低风险

本项目**面向单人自用**：一个人在**自己的服务器**上、用**自己的账户**、
交易**自己的资金**。这个形态通常不构成受监管的活动。

### 会显著改变风险的三件事

| 如果将来…… | 风险 |
| --- | --- |
| **替别人管理资金**（哪怕只是"帮朋友跑一下"） | 可能构成投资顾问 / 资产管理，**在多数辖区需要牌照** |
| **提供托管服务**（别人注册、把 API Key 交给你、你替他交易） | 同上，且叠加了**代客保管密钥**的安全与合规责任 |
| **出售策略或信号** | 可能构成投资建议，不同辖区规则差别很大 |

### 加密货币合约的特殊性

**加密货币衍生品（合约、杠杆）在多个辖区对零售用户是受限或被禁止的。**
本项目做的就是加密合约自动交易，所以：

- 面向零售用户分发这类工具，在某些辖区可能有额外要求
- 若将来做任何形式的商业化（收费、托管、白标），**必须先做辖区合规评估**

### 必须写进文档的风险提示

- 自动化交易**会造成真实资金损失**
- 本项目**不构成投资建议**，不对任何交易结果作出担保
- 使用者需自行确认其所在辖区允许进行加密货币合约交易

当前 [README](../README.md) 已有前两条，第三条建议补上（见第 6 节）。

## 5. 代码来源与原创性 【可技术确证】

### 结论：全部为独立实现

- **零个 Go 文件**（参考产品的技术栈是 Go，本项目 100% TypeScript）
- 依赖清单中**没有任何**第三方交易系统的包
- 仓库中不存在任何第三方交易系统的源代码、文案或资源文件

这一点已通过全仓库扫描确认。**记录在此的目的是留痕**：如果将来有人质疑代码来源，
这份文档 + 干净的依赖清单 + 无第三方源码的仓库内容，是可以核查的证据链。

### 关于界面设计

本项目第一阶段的界面参考了公开可见的产品形态（决策流、净值曲线、持仓表格等）。
**功能布局与信息架构通常不受版权保护**，但**具体的视觉设计**（图标、配色方案、
插画、文案）可能受保护。

当前实现使用的是通用的深色终端风格、自研组件、开源图标与配色，
**没有复制任何受保护的视觉资源**。如果将来要靠近某个具体产品的视觉呈现，
建议先咨询律师。

## 7. 本文档的局限

必须说清楚：

1. **作者不是律师**，本文档不构成法律意见。
2. **无法在线核实条款原文。** 币安的服务条款页面对自动抓取返回 WAF 挑战（HTTP 202），
   本文中关于条款的内容来自工程实践中的观测与本项目的运行日志，
   **不是对条款原文的引用**。引用具体条款时必须由人打开页面确认。
3. **辖区差异巨大。** 本文档刻意不针对任何具体国家或地区给出结论 ——
   那需要知道你在哪里、你的用户在哪里。
4. **本文档会过时。** 监管环境、交易所条款、依赖许可证都可能变化。
   建议每次重大版本发布前重新过一遍第 6 节的清单。
