## 我要动手做什么

### 「想复核'这个功能还值得留吗'」
```bash
bash scripts/jev-review.sh
```
**一条命令给你七个判据**：
```
① 主判据：可执行率（保留组 vs 筛除组），自动分段统计"窗口判断前后"
② 追高占比（保留组里 24h >10% 的）
③ 系统性歧视（0% 保留率的标的占比）
④ 运行健康（Jev 失败次数、最近 5 轮决策耗时）
⑤ 网关契约（magpie 版本、模型数、mismatch）
```

**判定阈值：**
```
比值 ≥1.5   ⇒ POSITIVE，保留
比值 ≤0.67  ⇒ NEGATIVE，移除（删掉 .env 里的 AQ_JEV_PREFILTER=on）
0.67~1.5    ⇒ NEUTRAL，继续观察
```

### 「想重新采集样本」

bash scripts/jev-sample2.sh        # 手动采一次

写入 `data/jev-samples.jsonl`（不受日志轮转影响）。

## 三条必须记住的教训

### ① 决策模型的输出质量取决于你喂什么

```
同一批标的、同一个 Jev、同一套问题：
  只给行情数字      → 按"波动大小"排，保留组可执行率 20.5%
  加一行"窗口判断"   → 按"是否在可执行窗口"排，保留组可执行率 66.7%
```

**业务知识应该由代码算好喂给它，不是让它猜。**

### ② 判据必须与被测目标对齐，否则会得出反向结论

```
用"波动大小"当判据：14 倍 POSITIVE  ← 让"Jev 在帮倒忙"完全隐形
用"可执行率"当判据： 0.51 NEGATIVE  ← 真相
```

**判据错了比代码错了更危险：代码错了测试会红，判据错了会一路绿灯。**

### ③ 环形缓冲下的观测数据必须主动落盘

`runtime_logs` 是环形缓冲（500 条，**全局共享**）。实测 scope 分布
`llm 202 / store 138 / team 114 / jev 10` ⇒ Jev 的时间跨度只剩 40 分钟。

**这个坑今天踩了四次**（详见 `docs/AGENTS.md` §5.6）。

## 一句话总结

> **Jev 的正确定位是「便宜的初筛」，不是「聪明的筛选器」。**
> 它能做：把 20 个标的砍到 6 个，省 70% 的逐币深看成本（308s → 73–104s）
> 它不能做：理解"这个位置还能不能进"、产出任何文字理由
> **不要期待它提升决策质量。它的价值就是省钱，而省钱这件事它做得很好。**
