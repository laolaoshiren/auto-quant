# 需求②验证：事件驱动的持续工作，而不是定时轮询（2026-10-15）

> 需求原话：
> > 「系统不再是像现在这样**定时**去工作，而是**持续、并发**的工作，增加盈利的可能」

**结论：已实现，且线上数据支持"不是定时"。**

---

## 1. 判据

「不是定时」不能靠"代码里有事件驱动"来证明（那是"实现了逻辑"）。
可测量的判据是**轮次间隔的分布**：

```
若真是固定定时（周期 15 分钟）→ 间隔应当集中在 15 分钟附近，方差极小
若事件驱动在生效            → 间隔会【散开】（事件把它压缩或推迟）
```

---

## 2. 实测（`#11`，最近 40 轮）

```
间隔分布：min=3.4 · p25=9.5 · p50=12.1 · p75=17.2 · max=20.8 分
```

逐轮（节选，条长 = 间隔分钟数）：
```
第 256  10.1 分  ##########
第 258   9.6 分  ##########
第 262   6.0 分  ######
第 264   8.5 分  ########
第 266   6.2 分  ######
第 268   8.4 分  ########
第 269   3.4 分  ###          ← 远小于 15 分钟
第 270   4.5 分  ####
第 271   9.9 分  ##########
第 260  20.4 分  ####################   ← 大于 15 分钟
```

**而配置的周期是 15 分钟** ⇒ 间隔能低到 **3.4 分**、高到 **20.8 分**，
说明确实有东西在改变节奏 —— 那就是事件驱动。

---

## 3. 触发源（`agent_runs.trigger`）

```
idle            41   ← 空闲（没有新信息时的兜底心跳）
new_result      20   ← 有新结果（成交/平仓回来）
losing_streak   18   ← 连亏
timeout         17   ← 超时
rejections       3   ← 决策被拒
```

**5 类触发源**，其中 `new_result` / `losing_streak` / `rejections` 是**事件**，
`idle` / `timeout` 是**兜底**。⇒ 与需求②"总管根据资料反馈做处理"的形状一致。
