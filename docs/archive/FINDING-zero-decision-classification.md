# 空决策轮的完整分类，以及"故障 vs 观望"的界面修复（2026-10-15）

> ⚠️ 本文的核心价值不是那条 UI 修复，而是**判据是怎么定的** ——
> 我在这里连续错了三次，每次的错法都不同。

---

## 1. 症状：界面把故障说成判断

`DecisionDetailPage` 对"零决策"只有一句文案：
```
没有可执行的决策 — 本周期模型选择观望或持仓。
```
而线上真的有两种**性质完全不同**的情况被它混成一句：
```
① 模型判断不做（一个【判断】）        —— 正常
② 裁决环节失败（一个【故障】）        —— 需要排查
```

**危险之处**：说成"模型选择观望"之后，**没有人会去查它**。

---

## 2. 判据的三次错误（这是本文最有价值的部分）

### 第一版：只认我预想的措辞 → **漏报**

```ts
/解析失败|被截断/     // ❌ 线上真实用词是「没有找到 JSON 数组」
```

### 第二版：把"同义词"都列上 → **误报率 64.4%**

```ts
/解析失败|无法解析|不可解析|解析不出|被截断|截断/
// 非空轮 160 个里误报 103 个
```

逐条看原文后找到原因 —— **「截断」这个词在 `raw_response` 里到处都是**，
描述的却是**别的地方**的截断：
```
第  4 轮：「cline/…/step-5-preview → 输出被 token 上限截断，加大 max_tokens 重试」
          ← 模型降级链的日志，与本轮成败无关
第  5 轮：「多空论证均被截断(做多第三部分缺失)」← 某角色产出被截，但本轮 20 条决策正常
第 85 轮：「bear虽然论证被截断，但方向正确」  ← 【裁决官在引用它看到的失败】
```

**共同点：这些轮次都有正常决策**，而我全判成"故障"。

### 第三版：**穷举**「只出现在空决策轮」的报告行 → 正确

把 264 条记录里所有"系统在报告本轮异常"的行抽出来，按「是否只在空决策轮出现」筛：

```
✅ 只在空轮出现（27 次）: ⚠️ 裁决里没有找到 JSON 数组 —— 模型可能只写了散文
✅ 只在空轮出现（ 6 次）: ⚠️ 裁决里的 JSON 解析失败（可能被截断）
❌ 两种轮次都出现（192 次：空 74 / 非空 118）—— 不能当判据:
   ⚠️ 本轮未经风控官审阅（风控角色未启用或调用失败）
```

**最后那条特别值得记**：它看起来很像"系统坏了"（"未经审阅""调用失败"），
但它**在正常轮次里也出现** —— 因为风控官本来就不是每轮都启用。
拿它当判据会**误报 74 次**。

### 实测结果（线上 264 条）

```
空决策轮 104 个 → 识别 33 · 未识别 71
非空轮   160 个 → 误报 0 ✅
```

## 3. 空决策轮的完整构成（104 个）

| 类别 | 个数 | 性质 | 时间 |
| --- | --- | --- | --- |
| A 裁决 JSON 解析失败（截断） | 6 | **故障**（已修：预算 8192→16384） | 10-15 |
| B 裁决里没有找到 JSON 数组 | 27 | **故障**（两种子类，见下） | 10-12 → 10-14 |
| C 没有 `<decision>` 块 | 1 | 异常 | 第 2 轮 |
| E 真观望（模型给 `[]`） | 67 | **正常** | — |
| F 有内容却没入库 | 3 | **BUG** | 第 70/84/192 轮 |

### B 类拆成两个子类（27 个）

```
① judge 返回【散文】而无数组      20 个
   原文：judge（group/auto-muse-spark-1-3-contributor）：结论：**不行动**
   ⇒ 提示词遵从性问题（它"裁决"了，但没按格式给数组）

② judge 【调用失败】               7 个
   原文：judge（（未调用成功））：失败 —— OpenCode Go: Upstream request failed:
        This Go model trains on request data. Allow paid endpoints that train
        on request data in your workspace's Privacy settings to use it.
   ⇒ 供应商侧问题（OpenCode Go 的隐私设置）
```

⚠️ **这两类都在 10-12 → 10-14，即"补 7 角色提示词"之前** ——
不是那次改动引入的。

### F 类：模型给了决策却没入库（3 个，第 70/84/192 轮）

```
第 70 轮：<decision> 块 = [{"symbol":"WUSDT","action":"s…   ← 模型给了决策
          而 decisions_json = []                             ← 存储里是空
```

这与我 10-15 修的 `b8f33a6`（非法 `entry_type` 丢整条决策）**同形** ——
当时实测是"那两轮的 `decisions_json` 都是 `[]`，而 `<decision>` 块里明明有 6 条"。
第 70/84 轮（10-13）早于该修复。

## 4. ✅ 一个重要的**否定**结论：状态行没有说谎

一度怀疑「已裁决」这个状态词与 judge 失败矛盾。查清后：

```
verdict?.ok ? '已裁决' : '未裁决'

judge 调用失败时 → 状态行说「未裁决」7/7 全部一致 ✅
「已裁决」出现在散文类那 20 个里 —— 因为 judge 确实【成功调用】了，只是没给数组
```

⇒ **状态词是准确的**。我原来的怀疑不成立（这是本轮第 2 个被我推翻的猜测）。

## 7. 一条可复用的方法论

这三版判据的演进，本质是同一个问题的三次不同表现：

```
第一版错误：判据只覆盖【我预想的措辞】         → 漏
第二版错误：把"语义相近"的词都加进来           → 误报
第三版正确：【穷举数据里所有候选信号，          → 用数据筛，
            按"它是否只在该状态出现"来筛】        不用我的语义直觉
```

**判据的来源应当是数据，不是我的想象。**
—— 这与仓库里那条既有纪律同源："判据必须能区分『我要检查的东西』与『别的东西』"。
