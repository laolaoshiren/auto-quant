# 发版说明的格式

> 这份文件的唯一目的：**下一次发版时不用再问"该怎么写"**。
>
> 参照对象：[yetone/magpie 的 Releases](https://github.com/yetone/magpie/releases)。
> 用户的原话：「你这发版说明怎么又写成流水账了，搞简洁标准的啊，你就模仿 magpie 人家怎么写的来弄就行了」。

---

## 一、结构（固定三节，按需出现）

```markdown
## Features
- 一句话，动词开头。

## Bug Fixes
- 一句话，说清"修了什么"。

## Improvements
- 一句话。
```

- **没有内容的那一节整节省略**（不要留空标题，也不要写 "No changes"）。
- 节标题只用这三个：`Features` / `Bug Fixes` / `Improvements`。
  需要冒烟测试的破坏性改动单独加 `## Breaking Changes`，并放在最前。

## 二、每条怎么写

**一条 = 一行 = 一件事。** 判据：

| ✅ 正确 | ❌ 错误 |
|---|---|
| `- 历史成交的时间列移到最左，与当前委托、订单记录一致。` | `### 历史成交的时间列调整` + 三段解释 + 表格对照 + 为什么这么做 |
| `- 修复被截断的 JSON 仍显示原文。` | `- 修复了在 `structuredMessage.ts` 的 `parseLooseObjectDetailed` 里，当 `tail.truncated` 为假时……（40 行）` |
| `- 停摆告警阈值改为跟随真实轮次分布。` | `- 用户反馈说一天误报两次，我查了很久发现……（复盘过程）` |

**具体规矩**：

1. **动词开头**：`修复…` / `新增…` / `改为…` / `移到…` / `关闭…`
2. **不写实现细节**：不写文件名、函数名、行号、变量名 —— 那是 commit message 的事
3. **不写"为什么"**：代码注释里已经写了；发版说明只说"变了什么"
4. **不写复盘过程**：不写"我一开始以为…后来发现…"
5. **不给对照表格**：除非是破坏性变更需要迁移前后对比
6. **一条不超过 40 字**（中文）；超了说明它在说两件事，拆开
7. **结尾不加"---"分割线和免责声明**（`⚠️ 这个项目下的是真实订单` 那句已经写了三遍，删掉）

## 三、必须有的 `### Install`

```markdown
### Install

`pwsh -File scripts/deploy.ps1`（本项目不走 Docker）。
```

一段话，固定。**不要**写成 magpie 那样的多平台下载列表 —— 本项目没有二进制分发。

## 四、不要写的东西（清单）

- ❌ 「## 这一版解决的事」这类开场白
- ❌ 「已知未解」小节（那是缺陷台账的职责，不是发版说明的）
- ❌ 任何 `⚠️` 警告块
- ❌ 数字统计（"修了 9 项"、"89 处 → 6 处"）—— 那是验证报告的事
- ❌ 表情符号（📊 ✅ 🎯 等）
- ❌ `---` 分割线
- ❌ 中英混排的节标题（统一用 `Features` / `Bug Fixes` / `Improvements`）

## 五、自检

发版前对着这几条过一遍：

```
□ 总长度 < 1500 字节？
□ 每条都在 40 字以内？
□ 没有文件名/函数名/行号？
□ 没有"为什么"和复盘？
□ 没有表格？
□ 空节已省略？
□ 最后是 ### Install？
```

> **参考量级**：v0.1.43 的说明是 **1,116 字节 / 9 条**。那是一个「改了 3 个文件」的版本。
> 如果一次发版有 20+ 条，那说明发布频率太低了 —— 该拆成多次发布，而不是把 20 条塞进一次。

---

## 六、怎么写（操作步骤）

发版时：

1. 写 `RELEASE_NOTES_v<版本>.md`，按上面的结构
2. `git tag -a v<版本> -m "v<版本>"`
3. **先推 tag**（不推 tag，`gh release create` 会报 `tag exists locally but has not been pushed`）
4. `gh release create v<版本> --title "v<版本>" --notes-file RELEASE_NOTES_v<版本>.md`
5. `git push origin main`
6. `pwsh -File scripts/deploy.ps1`
7. 回读 `build-info.json` 的 `commitShort` == 本地 HEAD

> ⚠️ **顺序很重要**：`gh release create` 之前必须推 tag，否则会失败。
