## 一、修掉的两个缺陷（都是实测发现，都不报错）

### 1. 模型的原生工具调用格式没被接住（正在烧钱）

```
#2  [timeout/panel] failed  6 步  25621/4725 tokens  39992ms
    模型连续两轮没有输出可解析的工具调用
```

**Command 厂商的模型用它训练时的原生工具调用语法回来**，而解析器只认提示词里
要求的 JSON。后果：**那一轮审视作废 + 2.5 万 tokens 白烧**，日志里只显示
"模型没输出可解析的工具调用" —— **看起来像模型不听话，实际是"我们没接住它的话"。**

**修法**：新增原生格式解析器，`parseTurn` 先试 JSON、不认再试它。
**只多认格式，不放宽语义**：抽出来的工具名与参数照样过原来的校验
（一个幻觉工具名在两种方言下都被拒，有用例钉住）。

**修复后**：

```
#3  [timeout/panel]  ok  6 步  22638/2857  25823ms
    模型在第 6 步自行结束。
```

### 2. 实验记录里的 `tool_calls` 一直是空的

每一条调参实验的 `tool_calls_json` 都是 `[]`，**而同一个文件里我写着**
"用一个引用盒子，`set_params` 发生时把当前步骤快照进去"。

**那句话是错的**：闭包返回的是引用，而赋值在循环结束之后 —— 那一刻它还是空数组。
**结果是每条调参实验都丢了它的推理依据**，而字段在、类型对、只是永远为空。

**修法**：循环每步实时回调。变异检查：去掉接线 → 用例立刻变红。

## 二、机器人不交易 —— **不是故障，是正确执行了一套过严的参数**

### 证据：模型自己的结论（原文摘要）

> 最高周期（4H）仍偏空、1H 偏多、短周期无方向，属于典型的**互相冲突情景**。
> 按要求，信号冲突时正确的动作是 wait。BTC 与 ETH 都找不到**既能守住 0.30% 最小止损、
> 又有清晰失效位和至少 1:3 盈亏比**的入场点，**置信度达不到 80 的门槛**。
> 空仓等待，本金零风险。

### 三个约束叠在一起

| 约束 | 来源 |
| --- | --- |
| 最小止损 0.30% | `minStopLossFeeMultiple: 3`（= 3 × 往返手续费） |
| 盈亏比 ≥ 1:3 | `minRiskRewardRatio: 3`（稳健预设） |
| 置信度 ≥ 80 | `minConfidence: 80`（稳健预设） |

**候选池里有 BTC/ETH**（所以开仓在算术上可能），但行情本身是冲突的
（4H 偏空、1H 偏多），三条门槛一起过不去。

### ⚠️ 这里有一个死循环，AI 自己也看到了

它第一次调参的理由里写着：

> 把 `minPositionSize` 从 12 降到 6，使最小下单量与当前账户规模兼容，
> **从而首次产生真实的入场/拒绝样本**。

**它知道需要样本才能学。但样本要等它开第一笔仓 —— 而它因为参数过严开不了仓。**

**这不是我能单方面解的**：放宽盈亏比/信心门槛是**动风险参数**，
而 `AGENTS.md` §4.2 明确不让代理为了让东西"跑通"去放宽它们。**那是操作员的决定。**

其余全是行情数据）。
