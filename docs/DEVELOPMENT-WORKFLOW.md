### 0.2 三条不可协商的前提

1. **这是动用真实资金的系统。** 风控引擎 `packages/server/src/risk/engine.ts` 是通往订单的
   **唯一路径**；任何绕过它的下单路径都是 blocker 级缺陷，不是"优化空间"（[`AGENTS.md`](AGENTS.md) §2.1）。
2. **历史代价换来的硬约束：提交信息只有一行。** 本项目曾因技术报告式提交信息，
   231 个提交合计 **20.9 万字符**（最长一条 91 行），最后不得不重写全部历史。
   所以"一行"不是风格偏好，是**不可回退的历史教训**。
3. **站点专属信息绝不进入被跟踪的文件。** 域名 / IP / 主机名 / 服务器路径 / 凭据 ——
   在代码、注释、日志、测试夹具、文档示例、提交信息里一律用占位符：
   `my-server`、`/srv/<应用目录>`、`https://quant.example.com`。
   一次性报告与台账放在**不入库**的 `.dsh/`（`.gitignore` 已忽略）。

### 0.3 术语

| 术语 | 含义 |
| --- | --- |
| **条目（item）** | 台账里的一条缺陷、风险或需求，有唯一 ID，直到关闭才会消失 |
| **闭环** | 独立验证通过 **且** 独立审查通过 **且** 闭环核验通过 |
| **写作用域** | 一次任务中允许改动的路径集合；写作用域互斥的成员可以并行 |
| **证据来源** | 能被人独立复现的定位：`命令 + 退出码 + 输出片段`、`文件:行号`、`线上回读的值与时间点` |
| **轮次** | 同一条目的一次"修复 → 验证 → 审查"往返；审查不通过就进入下一轮 |

## 1. 提交规范

### 1.1 硬约束（违反即不合规）

| # | 约束 | 判据 |
| --- | --- | --- |
| 1 | **只有一行标题**，没有正文、没有 `## 起因` 这类小节 | `git log -1 --format=%B` 去掉尾随空行后只剩一行 |
| 2 | 格式 `<type>(<scope>): <描述>`；type 必填，已知域必填 scope | §1.2 / §1.3 |
| 3 | 标题 ≤ **72 字符**（建议 ≤ 50），不含换行 | 超过 72 字符的提交历史上有 126 条，是"读不完"的主要来源 |
| 4 | 不含站点专属信息 | 域名 / IPv4 / 主机名一律不出现 |
| 5 | 不写对话过程、用户原话、轮次编号 | 出现「第 N 轮」「补记」「顺便」「临时」「试试」即为不合规 |
| 6 | **一个提交只做一件事**；跨子系统的改动拆成多个提交 | 混合提交无法被审查、无法被单独回滚（[`MAINTENANCE.md`](MAINTENANCE.md) §1.1） |
| 7 | 破坏性变更在 type 后加 `!` | 例：`feat(risk)!: 策略配置新增必填字段` |
| 8 | 顺序是**先 commit 再 deploy** | 见 [`RELEASING.md`](RELEASING.md) 的「实盘部署闸门」 |

> 「为什么这么改」**不写进提交信息**：写在代码注释里（`AGENTS.md` §5.1），
> 或写进 `docs/` 的正式文档。过程性记录写进 PR 描述或 `.dsh/` 的报告。

### 1.2 type 取值清单

| type | 什么时候用 | 发布说明分类 / 版本增量（release-drafter） |
| --- | --- | --- |
| `feat` | 新增对外可见的功能或能力 | 🚀 新功能 → minor |
| `fix` | 修复缺陷（含回归） | 🐛 修复 → patch |
| `perf` | 只改性能，行为不变 | ⚡ 性能 → patch |
| `refactor` | 不改变行为的重构 | 🔧 其他 → patch |
| `test` | 只改测试与守卫 | 🔧 其他 → patch |
| `docs` | 只改文档、注释 | 📚 文档 → patch |
| `build` | 构建脚本、依赖清单、打包方式 | 🔧 其他 → patch |
| `ci` | CI 工作流与仓库自动化 | 🔧 其他 → patch |
| `chore` | 杂项（清理、忽略项、配置） | 🔧 其他 → patch |
| `revert` | 撤销某个提交（标题里写明撤销哪个） | 🔧 其他 → patch |

- **不要新增自定义 type**：type → 标签 → 发布说明分类 → 版本增量是一条链
  （`.github/workflows/pr-labeler.yml` → `.github/release-drafter.yml`），
  要加 type 必须三处同步改，并更新本表。
- 破坏性变更的判定（哪些算破坏性）见 [`RELEASING.md`](RELEASING.md) 第 1 节。

| 仓库配置与依赖 | `ci` / `deps` | `.github/**`、`package.json` |

**禁止的 scope 写法**（历史都出现过，新提交不再沿用）：

- 无信息量的 scope：`misc`、`general`、把 `test` 当 scope 用；
- 组合 scope：`logs,ui`、`ui,team`、`web,server`；
- 用 `+` 连接：`ui+manager`；
- **同一域两个名字**：`web` 与 `ui` 只能选一个 —— **新提交统一用 `web`**（历史里的 `ui` 保留）。

一个提交跨多个域时：**选风险最高的那个域**（碰了下单路径就写 `risk` / `trader`），
其余域写进描述，而不是塞进 scope。

### 1.4 描述怎么写

模板：**`<动作> <对象>，<结果或影响>`**（一行说完，不需要主语）。

| 要做 | 不要做 |
| --- | --- |
| 动词开头：修正、新增、删除、拆分、改为、撤销 | 「更新了一下」「调整」「优化」这类没有对象的动词 |
| 写清对象与结果：`拆分 clampStopLoss 与 clampTakeProfit，恢复止盈方向` | 只写过程：`改了一版` |
| 用稳定的机器码 / 字段名（`-4120`、`CLOSE_REASONS`） | 用口语代替标识符（「那个单子」「掉下来的那个」） |
| 具体数字写在描述里：`预算 8192→16384` | 用「大了一点」「差不多」 |
| 一件事一个提交 | 用「顺便」「以及」「另外」把多件事串起来 |

**禁用词**（出现即打回）：第 N 轮、补记、顺便、临时、试试、一些、貌似、大概、
差不多、修复了一下、某些情况、可能吧。

**引用 issue 号**：允许放在标题末尾（`（#123）`），因为本项目禁止正文承载这类信息。

### 1.5 正反例对照（反例全部取自本仓库真实历史）

| 反例（真实提交） | 问题 | 改成 |
| --- | --- | --- |
| `docs: 补记第 49 轮 —— eslint-disable 复查与 usePolled 纪律守卫、v0.1.38` | ①「第 49 轮」对外没有任何意义；②三件事塞进一行，谁也不知道这次到底改了什么；③把版本号写进 docs 提交（版本号由发版流程管） | `docs(archive): 归档第 49 轮审计记录`；同批次里真正的代码改动**单独提交**：`test(web): 守卫 usePolled 不得被条件调用` |
| `feat(intel): 新增消息面猎手模块 hunters（多源调研的前置件，本轮未接线、零行为改变）—— 用户要求'有调查新闻的/有监控社区的/…'`（>200 字符） | ①超长，`git log --oneline` 直接折行；②引用私下对话（公开历史不该有）；③写进「本轮未接线」这类**会过期的状态** | `feat(intel): 新增消息面猎手，覆盖新闻/资金/社区/宏观四个来源` |
| `ci: 临时探测工作流（用完即删）` | 「临时」写进永久历史；若该工作流后来没删，历史就等于在撒谎 | `ci: 增加工作流触发探测`；真删掉时再提交 `ci: 移除工作流触发探测` |
| `chore: 清掉临时验证脚本` / `chore: 清掉临时验证脚本及其忽略项` / `chore: 清掉临时验证脚本的忽略项` / `chore: 临时验证脚本不进版本库` | 同一件事散成 4 个提交，`git log` 读不出发生了什么，回滚也没有边界 | 合并成一次：`chore: 清理本地验证脚本及其忽略项` |
| `docs: 记录 UI 验证方法（含旧隧道残留导致假失败的坑）` | 口语「坑」；没写清改的是哪份文档、给谁看 | `docs(workflow): 补充 UI 验证方法与隧道残留导致的假失败` |

**正例（同样取自真实历史，可直接照抄写法）**：

```

```

### 1.6 校验现状（诚实说明能自动拦什么）

| 检查 | 由谁执行 | 能拦什么 | 拦不住什么 |
| --- | --- | --- | --- |
| 一行标题 | `packages/server/src/commitMessageGuard.test.ts`（`npm test`） | 最近 50 个提交里的多行信息、空主题 | 历史老提交；超过 50 个之前的违规 |
| 不含站点信息 | 同上 | 裸 IPv4、形如真实域名的字符串 | "看起来不像站点信息的普通域名" |
| 凭据格式 | `scripts/pre-commit.sh`（本地钩子）+ CI 密钥扫描 | `sk-…`、`ghp_…`、私钥块、硬编码密钥赋值 | 站点专属信息（需 `sensitive-patterns.txt`，本机 gitignored） |
| 站点专属信息（别名/主机/路径） | **只靠本地** `sensitive-patterns.txt` | 该表里逐条登记的形状 | ⚠️ 两道结构性边界（实测）：① 那张表**每台机器各自维护**，换台机器就失效，CI 也拿不到它；② 钩子只扫**本次暂存的增量**（`git diff --cached`），**扫不到历史**。所以**已入库内容里的别名/主机名不会被任何一道自动检查拦下** —— 这类问题只能靠 review 与"归档/提交前脱敏"（§3.6） |
| 长度、type/scope 合法性、语义质量 | **没有自动化** | —— | 只能靠 [`COLLABORATION.md`](COLLABORATION.md) 闸门⑤ 与人工 review |

- 未推送的提交可以用 `git commit --amend` 修正标题；
- **已经推送的历史不重写**（重写历史会打断别人的基线）；
- 发现别人（或自己早先）的违规写法：**在 review 里指出，从下一个提交改起**，
  不要为了标题去开一堆"改标题"提交。

**别名类信息的巡检命令**（人工判断，**不要**改成自动阻断；实测跨 PowerShell / bash 结果一致）：

```bash
git grep -nE '(ssh|scp)[[:space:]]+[A-Za-z][A-Za-z0-9_.-]*' -- .
```

它列出"`ssh` / `scp` 后面跟一个词"的**候选行**，由人判断该不该替换成占位符。
**这条命令是自证的**：跑它得到的结果就是当前状态；下面是同行核对过的基线读数 ——
**2026-10-17：3 个候选 = 2 个真实别名 + 1 个合法占位符**（带日期是为了让它在阶段 2 清理之后
**过期而不算错**：清理完成后读数应变成 1 个候选）。两点注意：

- 模式要求 `ssh` 后**紧跟空格**，所以 `ssh-add` / `ssh-keygen` 之类不会被命中；
- `[A-Za-z0-9_.-]*` **没有长度上界**，原则上会命中"`ssh` 后面任何以字母开头的词" ——
  这正是它只适合作**人工巡检**的原因：裸别名没有通用可判定形状，写成自动阻断必然误报，
  而误报会训练人绕过检查（`scripts/pre-commit.sh` 开头自己写了这条原则）。
  命令**无转义字符、范围写全（`-- .`）**，这是为了能在任何 shell 里原样复现（§4.7 硬规则 7）。

## 2. 验证阶梯：每一档能证明什么

> 权威表与逐档命令在 [`AGENTS.md`](AGENTS.md) §6.1 / §6.2。本节只讲**怎么用**。

| 档 | 手段 | 能证明 | **证明不了** | 成本 |
| --- | --- | --- | --- | --- |
| ① | 单元测试 | 纯逻辑：解析、每条风控限制与钳制方向、指标数学、账目算术、字段映射 | 任何需要真实网络 / 交易所行为 / 时间推进才暴露的问题 | 无 |
| ② | `npm run sim` | **接缝**：保护单是否真挂上、触发后是否真记账、权益曲线是否推进、冷却/节流、风控是否真在路径上 | 真实模型的指令跟随、真实交易所的接口契约 | 无 |
| ③ | `npm run sim:live` | 真实模型能否按格式输出、真实提案能否通过风控 | 真实交易所的**交易接口接线** | **花 LLM 的钱** |
| ④ | `npm run demo` | 完整审计链路在真实库与控制台里的呈现 | 交易正确性（它的模拟 broker 不触发保护单） | 无 |
| ⑤ | 实盘冒烟（`liveSmokeTest.ts --confirm`） | **接线**：预检→杠杆→开仓→挂止损止盈→**回读交易所确认**→撤单→平仓→账户干净 | 长时间行为、策略盈利能力、并发场景 | ⚠️ **真实资金** |
| ⑥ | 真实交易 | 一切 | —— | ⚠️ **真实资金** |

**使用规则**：

1. **从最低档开始，只在上一档证明不了时才往上走。** 不为了"更保险"直接跳档。
2. 碰下单路径的改动 → **至少到 ②**；`AGENTS.md` §6.1 说 ② 证明的是接缝，不是接线。
3. 断言依赖**外部系统**（币安字段、LLM 方言、端点形状）→ 必须真实环境验证，
   或明确写「未在真实环境验证」，**不允许含糊**。
4. **③⑤⑥ 有真实成本。** AI 成员**不得自行触发**：需要时先向队长说明理由与清理步骤，
   得到确认再跑；跑完回报实际花费与清理结果。
5. 任何"验证通过"的声明必须带上：**跑了哪一档、命令原文、退出码**。
   「我读过觉得对」不是验证。

### 2.1 历史坑：命令接管道后退出码是假的

PowerShell 里 `$LASTEXITCODE` 是**最后一条外部命令**的退出码，不是管道上游那条的：

```powershell
# ❌ 错：这个 $LASTEXITCODE 是 Select-String 的，永远 0
npm run typecheck 2>&1 | Select-String "error TS"; "exit=$LASTEXITCODE"
```

```powershell
# ✅ 对：让它别接管道，重定向到文件再读
npm run typecheck > $env:TEMP\tc.log 2>&1
if ($LASTEXITCODE -ne 0) { Get-Content $env:TEMP\tc.log | Select-String "error TS" }
```

这个仓库为此**连续多轮误报 typecheck 全绿**，直到某次没接管道才发现一个一直存在的 TS7016。
所以：**报告验证结果时贴退出码本身**，不要贴一段被过滤过的输出。

### 2.2 不要在文档里写死用例数

`npm test` 的规模看它自己打印的 `# tests`。文档里写死数字一定会腐烂
（这个仓库已经发生过多次），所以本文只写"必须全绿"。

## 3. 可持续闭环流程（本项目的核心流程）

> 用户明确要求：「应该是可持续进行的……开发完成一个-提交以后，另外员工检查出问题，
> 是否会开始进行流程复查-核实-重新修复开发，一套完整的流程，而不是一次性的，
> 做完就丢着不管了，最终留下一堆烂摊子等我来收场。」
>
> 所以：**任务结束不等于问题解决。** 只有台账条目走完闭环，工作才算结束。

### 3.1 循环图

```
  ┌──────────────────────────────────────────────────────────────────────────┐
  │                                                                          │
  ▼                                                                          │
发现 ──→ 台账登记 ──→ 需求与验收标准 ──→ 实现 ──→ 提交                       │
（审计/巡检/用户反馈）        （写作用域分派）                                │
                                                    │                        │
                                                    ▼                        │
                                            独立验证（≠实现者）               │
                                                    │                        │
                                        ┌──── 不通过 ┴──── 通过 ───┐          │
                                        ▼                          ▼          │
                                     修复回环                  独立审查       │
                                  （回到"实现"）              （≠实现者）      │
                                                                  │          │
                                                    ┌── 不通过 ────┴── 通过 ──┤
                                                    ▼                        ▼
                                                 修复回环                闭环核验
                                              （下一轮审查）          （原点复现+无回归）
                                                                             │
                                                                  ┌─ 不通过 ─┴─ 通过 ─┐
                                                                  ▼                  ▼
                                                               修复回环          集成与回归
                                                                                     │
                                                                                     ▼
                                                                             阶段性发版
                                                                           （见 RELEASING.md）
                                                                                     │
                                                                                     ▼
                                                                                  下一轮
```

**关键：任何一步不通过都回到"实现"，且下一轮必须重新走验证与审查 —— 不存在"跳过审查直接发版"。**

### 3.2 每一环：责任人 / 准入 / 退出 / 失败回退

| # | 环 | 责任人 | 准入条件 | 动作 | 退出条件 | 失败时回到哪一步 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | **发现** | 任何成员 / 用户反馈 / 定期巡检 | 有一个可指认的现象（日志、线上回读值、用户描述、代码位置） | 记录：现象 + 证据来源 + 影响面（是否碰资金/风控/线上） | 形成一条候选，交给台账官 | 无法复现 → 记入台账「观察项」，**不丢弃、也不当缺陷** |
| 2 | **台账登记** | 缺陷台账官 | 候选带现象与证据来源 | 分配 ID、定严重度（P0–P3）、登记字段（§3.4） | 状态 `NEW → DEFINED` | 证据不足 → 退回发现人补证据 |
| 3 | **需求与验收标准** | 缺陷台账官（必要时与领域负责人一起） | `DEFINED` | 写下：期望行为、**可执行的验收标准**、需要哪档验证、写作用域 | 状态 `DEFINED → READY` | 验收标准无法判定 → 退回第 2 步重写 |
| 4 | **实现** | 实现者（按写作用域分派） | `READY` 且该写作用域空闲 | 改代码 + 加测试（修 bug 必须带"没修就会失败"的测试） | 本地最低门槛过（§2）；状态 `READY → IN_PROGRESS` | 卡住 → 条目写清卡点，上报队长，**不得静默放弃** |
| 5 | **提交** | 实现者 | 门槛过 | 按 §1 写一行中文标题；`git commit` | 提交哈希写进条目；状态 `IN_PROGRESS → IMPLEMENTED` | 不合规 → 未推送则 amend；已推送则从下一个提交改起 |
| 6 | **独立验证** | **验证者（≠ 实现者）** | `IMPLEMENTED` + 验收标准 + 提交哈希 | 在指定档位跑验收；记录命令、退出码、输出、时间 | 状态 `IMPLEMENTED → VERIFIED`；证据写入条目 | **不通过 → 回到第 4 步（修复回环）**；失败证据写进条目 |
| 7 | **独立审查** | **审查者（≠ 实现者；建议也 ≠ 验证者）** | `VERIFIED` | 过五道闸门 + 本批红线清单，逐行读关键 diff | 状态 `VERIFIED → REVIEWED`（verdict = pass） | **不通过 → 回到第 4 步**，findings 必须结构化（问题 / 严重度 / 要求的修法） |
| 8 | **闭环核验** | 缺陷台账官（可由一致性巡检官抽查） | `REVIEWED` | ① 回到**原点**确认原现象消失；② 确认无新回归；③ 验收标准逐条对照 | 状态 `REVIEWED → CLOSED`；闭环证据非空 | **不通过 → 回到第 4 步**，并标注是"未修好"还是"修出回归" |
| 9 | **集成与回归** | **未参与该批实现**的成员 | 本批条目集合已 `CLOSED` | 全量验证（typecheck / lint / test / build，必要时 sim）+ 跨条目回归 | 全绿；产物与记录留档 | 定位到具体条目 → 回到第 4 步；无法定位 → 新开一条 P1 |
| 10 | **阶段性发版** | 版本发布官（部署由线上运维官执行，需用户确认） | 满足 [`RELEASING.md`](RELEASING.md) 的「阶段性发版判据」**且**门禁全过 | 按发版流程执行 + 线上回读 | 线上回读一致；版本号四处对齐 | 回读不一致或健康异常 → **回滚**（见 RELEASING） |
| 11 | **下一轮** | 一致性巡检官 / 审计成员 | 任意时刻 | 抽查证据链：有无"查过了"但没证据的结论、有无被静默关闭的条目 | 新发现回到第 1 步 | —— |

### 3.3 四条硬规则

> 这四条是上表的**不变量**。任何与之冲突的"灵活处理"都不成立。

1. **未关闭条目不得消失。**
   任务可以结束、批次可以结束、会话可以中断，但台账条目**只有在
   「独立验证通过 + 独立审查通过 + 闭环核验通过」之后才能置为 `CLOSED`**。
   *任务结束不等于问题解决。* 禁止用"这批先到这里"把未闭环条目从视野里移走；
   禁止只在聊天里汇报、不落台账。

2. **审查不通过必须自动进入修复回环。**
   审查 verdict 为 needs_revision / reject 时，条目回到「实现」，然后**重新走验证与审查**。
   不得把失败的任务丢下不管，**更不得跳过审查直接发版**。

3. **验证者不得是实现者。**
   同一条目的实现、验证、审查必须是**不同的人**（同一成员不得同时担任两角）。
   这是独立性的底线；人手不足时**条目保持未闭环**并上报队长调度，
   **不是降低标准**、也不是让实现者"自己验证一下就行"。

4. **未过门禁的条目不得发版。**
   发版只针对**已闭环的阶段性进展**（判据见 [`RELEASING.md`](RELEASING.md)）。
   台账里仍有该发版范围内的 `NEW / DEFINED / READY / IN_PROGRESS / IMPLEMENTED / VERIFIED / REVIEWED`
   条目时，发版必须停下来 —— 要么闭环它们，要么明确把它们排除在本次发版范围外**并写进发布说明**。

### 3.4 缺陷台账（唯一的进度载体）

**位置**：`.dsh/`（`gitignore` 已忽略，绝不入库）。
建议结构：

```
.dsh/ledger/
  items.md            ← 台账主表（唯一事实来源）
  evidence/<ID>/      ← 每条的验证与审查证据（命令输出、回读值、审查 findings）
```

**条目字段**（缺字段即视为未登记完成）：

| 字段 | 说明 |
| --- | --- |
| `ID` | 唯一编号（如 `AQ-0142`），一经分配不再复用 |
| `严重度` | P0 资金/风控/线上不可用；P1 功能不可用或数据错；P2 体验与一致性；P3 打磨 |
| `现象` | 一句话，可被复现或被证据指向 |
| `证据来源` | `文件:行` / `命令 + 退出码` / `线上回读值 + 时间` |
| `期望行为` | 修好之后应该是什么样 |
| `验收标准` | **可执行**的判据（跑什么、看到什么算过） |
| `验证档位` | §2 里的哪一档（碰下单路径至少 ②） |
| `写作用域` | 允许改动的路径集合 |
| `实现者 / 验证者 / 审查者` | 三个**互不相同**的人 |
| `状态` | §3.4 的状态机取值 |
| `轮次` | 第几轮修复（审查不通过就 +1） |
| `闭环证据` | 最后一次验证与审查的证据位置；**为空则不得关闭** |

**状态机**：

```
NEW → DEFINED → READY → IN_PROGRESS → IMPLEMENTED → VERIFIED → REVIEWED → CLOSED
                              ▲              │            │           │
                              └──────────────┴────────────┴───────────┘
                                任何一步不通过 → 回到 IN_PROGRESS（轮次 +1）
```

- `CLOSED` 是**唯一**的终态；`CLOSED` 之后发现回归 → **新开一条条目**并关联原 ID
  （不要偷偷把旧条目改回进行中 —— 那会让"历史说过什么"无法追溯）。
- `观察项` 分区：现象存在但无法复现/无法定性的事项写在这里，
  **不计入缺陷数、也不阻塞发版**，但每轮巡检要看一次。

**台账的更新纪律**：任何人都可以**追加**证据；但**状态字段只由责任人（缺陷台账官）推进**。
追加是 append-only：不删除、不覆盖别人写下的证据 —— 矛盾就并列保留，由一致性巡检官核。

### 3.5 会话中断 / 上下文丢失后靠什么恢复

**答案：靠磁盘事实，不靠任何人的记忆。**

恢复顺序（新会话第一件事，逐条做完再动手）：

1. 读 `.dsh/ledger/items.md` —— 哪些条目没关闭、卡在哪一环、谁的活；
2. 读 `.dsh/` 下最近一次侦察/验证报告 —— 上一轮发现了什么、证据在哪；
3. `git log --oneline -20` —— 最近提交了什么，条目里记的提交哈希是否真的存在；
4. 线上回读（由有 SSH 授权的成员执行）：`build-info.json` 的 `commitShort` 与
   `/api/health` —— 线上到底在跑哪一版、是否健康（见 [`RELEASING.md`](RELEASING.md)）；
5. 把以上三者与台账对照，**发现不一致就写进台账**，不要用"应该是这样"补上缺失信息。

**禁止**：把"我记得做完了"当作已完成；把聊天记录当作唯一证据；
在没有读台账的情况下重新开始一轮（那正是"烂摊子"的来源）。

### 3.6 台账为什么不入库

- 台账与一次性报告里会出现**站点专属信息、线上回读值、未公开的缺陷细节**；
- 仓库是公开的，提交历史永久可搜（这正是"提交信息只有一行"的原因）；
- 所以：**长期有效的规则进 `docs/`，一次性的过程与证据进 `.dsh/`**。
  一份 `.dsh/` 报告里有价值的部分，沉淀成 `docs/` 文档或代码注释之后，
  才算是被"学到"。

**归档/搬运前必须脱敏（硬规则）**：任何内容**从 `.dsh/`（不入库）搬进 `docs/`（入库）**，
或把一次性报告**归档进 `docs/archive/`** 之前，必须把操作者环境信息替换成占位符 ——
`ssh <SSH 别名>`、`/srv/<应用目录>`、`my-server`、`https://quant.example.com`。

理由（两道防线在这里都失效）：

- `scripts/pre-commit.sh` 只扫**本次暂存的增量**（`git diff --cached`），**扫不到历史内容**；
- 本地脱敏表（`sensitive-patterns.txt`）是 **gitignore 的、每台机器各自维护**，换台机器就失效；
- 实测教训：仓库里确实存在 **`ssh <操作者别名>` 形式的入库内容**（脚本与一份一次性报告各一处，
  提交于引入时）—— 而操作者**早已**在本地脱敏表里登记了 SSH 别名。
  规则"声明了"却没生效，原因正是上面两条结构性边界。
  → 结论：**不要依赖"我有脱敏规则"这个错觉**；入库前逐处替换，是唯一可靠的环节。

## 4. 协作纪律

### 4.1 语言与沟通

- **团队协作一律用简体中文**：任务汇报、发现、结论、报告正文、给队长的消息。
- 代码、命令、路径、标识符、日志与错误信息**保持原样，不翻译**。
- 面向用户的文本用中文、机器契约用英文（`AGENTS.md` §5.2 的边界，不要自行改）。
- 汇报格式：**结果在前、简短、表格 + 少量必要细节**；不贴大段代码与日志原文。

### 4.2 写作用域隔离

1. 每个成员在一次任务里只有**一个已声明的写作用域**（路径集合）。
2. **不越界**：包括"顺手"的格式化、重命名、注释清理 —— 那是最常见的越界形态。
3. 需要改作用域外的文件 → **上报队长**，由队长协调或重新分派（**不得自己动手**）。
4. 只读批次里，任何成员都不得改业务代码；唯一例外是被明确授权的文档写作用域。
5. 同一路径**同时只能有一个写入者**；并行工作必须路径互斥。

### 4.3 依赖顺序

- 从台账取 `READY` 的条目工作；上游未闭环的条目，下游**等它 `CLOSED`**（或队长明确批准并行）。
- 一个条目依赖另一条目时，台账里写清 `depends-on: <ID>`，禁止"我先按旧的约定做"。
- 批次内的顺序原则：**减少风险的工作先于增加风险的工作**（`AGENTS.md` §2.9）。

### 4.4 谁验证、谁审查

| 领域 | 独立验证岗（≠实现者） | 独立审查岗（≠实现者） |
| --- | --- | --- |
| 风控 / 下单路径 | 交易安全官（穷举下单调用点） | 质量审查官 + 交易安全官 |
| 账目 / 对账 / 迁移 | 账目对账官、数据库迁移官 | 质量审查官 |
| 团队模式（编排/角色/路由/提示词） | 团队复现官（在真实运行路径上复现） | 质量审查官 |
| 前端 UI / UX | 界面体验官（真实浏览器 + 量测） | 质量审查官 |
| 非团队模式与三套模板 | 非团队模式官、模板界面官 | 质量审查官 |
| 部署 / 运维 | 线上运维官（只读回读） | 质量审查官 + 线上运维官 |
| 文档 / 流程 | 一致性巡检官 | 质量审查官 |

- **验证者不得是实现者**（§3.3 规则 3）；建议**审查者也不要兼验证者**，
  三者不同人是理想形态。
- 质量审查岗**不参与实现**：同一批次里既写代码又给自己发 pass 是不允许的。
- 具体成员以当批团队名单为准；本表给的是**领域 → 岗位**的对应关系。

### 4.5 跨域问题怎么升级

1. 先把发现写进台账（现象 + 证据来源 + 影响面）；
2. 给队长一条消息：**现象、证据、为什么超出我的写作用域、建议怎么处理**；
3. 在队长答复前**不动手**（尤其是"顺手修一下"）；
4. 队长协调后由新责任人接手，条目上更新责任人与写作用域。

**默认不碰的事**（无论何时）：GitHub 高频/批量自动化（见下）、
线上服务的写操作、任何涉及真实资金的下单动作、`.env` 与 `data/`。

### 4.6 GitHub 使用纪律（2026-10-17 起）

**正常使用 GitHub 是允许且需要的**：提交、推送、开 PR、发版（Release/Tag）、
跑 CI、让版本号与线上对齐 —— 这些都是正规工程该有的东西。

**仍然禁止**（历史真实事故的成因）：

1. `gh` 进循环轮询：`gh pr checks` 之类**绝不放进 `for` / `while`**；
2. 批量对多仓库 / 多 PR / 多 issue 操作；
3. 一分钟内连续 `git push`；
4. 一次迭代开一堆 PR（**一个迭代 = 一个 PR**）。

要等 CI 就**一次性看结果 + 长间隔**，或者停下来问人；失败就停下报告，
不要写循环重试十几次。

### 4.7 反幻觉纪律

> 一份说错了的文档比没有文档更糟：照着它做的人会白白损失几个小时。
> 这条纪律对**报告、结论、台账、提交信息**同样适用。

**证据三档**，写报告时必须落在其中一档：

| 档 | 表述 | 要求 |
| --- | --- | --- |
| **已验证** | 「已验证：`<命令>` 退出码 0；输出 `<片段>`」 | 必须能被别人用同样的命令复现 |
| **未验证** | 「未验证：需要 `npm run sim:live`（花 LLM 费用，未获授权）」 | 说明**为什么没验**、需要什么才能验 |
| **推测** | 「推测（依据：`文件:行`）：……」 | 必须写明依据，**且不得作为下游结论或发版依据** |

**硬规则**：

1. 每条结论都要能指出**证据来源**；不能指出来源的，就不能写进结论。
2. **禁止**把"我读过代码觉得对"写成"已验证"；禁止把别人的转述当一手证据。
3. **禁止**用测试全绿代替接线验证（`AGENTS.md` §3.2 的真实教训：
   类型全过、`-4120` 让止损根本没挂上）。
4. **禁止**把退出码被管道污染的"全绿"当证据（§2.1）。
5. 修了一个 bug 但**没能复现它** → 说出来，不要暗示已经验证过。
6. 发现别人的结论与自己看到的不一致 → 并列保留并标注，交由**一致性巡检官**核
   （特例是发现导致**代码丢失**的风险：立刻说，不等流程）。
7. **给出的命令必须能在别人的环境里原样跑出同样结果。**
   不要依赖某个 shell 的引号 / 转义语义，也不要把命令的扫描范围写窄到会静默漏掉目标。
   实测教训：一条含反引号转义的正则命令，在 PowerShell 里命中 3 条、在 bash 里 **0 命中** ——
   而**一个 0 命中的巡检命令会被当成"巡检通过"**。所以：
   报告里贴的命令要**无转义字符**、范围写全（例如 `-- .`），并注明它是在哪个环境跑的；
   给不出可复现命令时，宁可写"这一步我没能自动化核到"，也不要给一条跑不出结果的命令。

### 4.8 判据的三条硬要求（2026-10-17，三条都由真实事故换来）

> 这一节的三条都是**同一类病**：**判据看起来在检查，其实永远不会失败。** 它们比"没有检查"更危险——
> 没有检查时人会小心；有一条永远绿的检查时，人会放心。

**① 判据不得恒真。** `assert.ok(/x/.test(C) === false || true)` 这类"左半句 + 一个恒真的尾巴"整条永真。
- 实测事故：`trader/agent/perSymbolWiring.test.ts` 曾有一条这样的断言，**守卫从未生效过**；它是全仓最后一条，已被清除。
- 自检方式：把判据的**每一半**分别代入"违规输入"与"合规输入"，**两者必须给出不同结果**。

**② 判据的基准必须独立于被测对象。** 期望值**从被测对象自身派生**（例如
`resolvePreset(x).field === (x.patch.field ?? 默认值)`）时，"声明"与"解析"会**一起错、两边仍然相等**。
- 实测事故：`breakevenTriggerPercent` 那次——把缺陷原形**变异回模板**后，该测试**仍 15 passed / 0 failed**（连变异都不变红）。
- 这种形态**比恒真断言更难发现**：判据在动、看起来像真检查，只是**基准跟着被测对象一起漂**。
- 正确做法：期望值来自**独立来源**——独立常量、契约字面量、或审计过的基线。

**③ 负向校准必须包含"针对判据自身实现机制"的变异**，而不只是"针对被守卫的业务行为"的变异。
- 只有前者回答"**这个判据能不能被绕过**"；后者只回答"**它有没有在跑**"。
- 实测事故：`riskOnlyPath` 守卫的"禁 `this[`"是**字面匹配**，于是
  `const self = this; self.executeOpen(…)`（**连动态调用都不需要**）可以**在守卫绿灯下新增一个绕过风控的下单调用点**；
  同一守卫的调用点正则只认 `this.` 前缀，`const { executeOpen } = this` 同样不可见。
- 结论：**11 个用例全绿不构成"守卫有效"**。判据必须回答"换个写法还能不能拦住"。

**收窄边界是合格的做法，隐瞒边界不是。** 若某类形状无法穷举，就**写进判据头部的「它抓不到什么」清单**——
**一个诚实列出自己盲区的判据，比一个看起来更严的判据更有价值。**

**④ 判据的基准必须独立于被测对象**（见 ②）。同理适用于**报告**：报告里"当前是 3 个候选"这类读数，
要么带日期标注为基线快照，要么写成"命令自证"——**否则清理之后就变成了错**。

### 4.9 模型/平台侧错误必须重试，不要当成任务失败

> 用户裁定（2026-10-17）：「模型问题你要**最大可能重试**（因为高峰期上游服务商可能出现不可预料的问题，
> 不代表重试以后不会解决）」

**要点：区分"真实失败"与"瞬时错误"。**

| 现象 | 性质 | 处置 |
| --- | --- | --- |
| `PI_AI_ERROR` / `tool call written as text, cut short` | **瞬时**（上游模型侧） | **重新指派重试** |
| `subagent stopped` / 超时 / 上游 5xx | **瞬时** | 重试 |
| verdict = `needs_revision` | **真实缺陷** | 进修复回环（**不要**靠重试绕过） |
| `failed` 因 verify 不绿 | **真实问题** | 要么修，要么据实记录 |

**重试策略**：
1. **同一执行者重试**（模型侧问题与成员能力无关）；
2. **连续 ≥3 次**才考虑换人——换人的目的是**换一条推理路径**，不是绕过问题；
3. **队长接管是最后手段**（仅在用户明确要求、或重试 5+ 次且阻塞发版时）；
4. **重试时不要缩减任务契约**，但应把工作**拆成小步**（每次 edit/write 只改一处）——
   `PI_AI_ERROR` 的成因正是**单次工具调用体积过大被截断**，分步能直接缓解。

**反面教训（本批真实发生）**：`t60` 连续 3 次 `PI_AI_ERROR` 后，队长一度判定"成员不可用"并自己接管 ——
**这个判断违反了上述裁定**：那 3 次全是上游瞬时错误，正确做法是**继续重试（并改成分步写）**。

### 4.10 验证装置本身也会骗人：两个真实事故（2026-10-17）

> 来源：`t62` 独立验证（三条已上线修复，verdict=pass）**自曝的两个已纠正的坑**。
> 它们比"被验证的东西有问题"更危险 —— **因为你会因此得出错误结论，还以为自己验过了**。

**事故 ①：补丁打错位置 ⇒ 一次没测到那条路**
- 现象：要替换的那段标记在文件里出现 **3 次**，`indexOf` 只取第一个 ⇒ before 树**仍真连交易所** ⇒ 五场景全 503；
- 危害：对比表上"差异巨大"，看着像"修复效果显著"，其实**一次没测到目标路径**；
- 修法：把「补丁落在哪个函数内」做成**硬断言**（不是"找得到就行"，而是"落在 `liveExchangeView` 内"）。

**事故 ②：外部命令的读数不可靠**
- 现象：Windows 上直接 `execFileSync('npx', …)` 会失败（`npx.cmd` 需 `shell: true`），于是负向校准全是 `pass=?/fail=?`，被误读成"基线也是红的"；
- 危害：**读数不可靠 ⇒ 结论不可靠**，而且"基线红"会让你以为"判据本来就有问题"；
- 修法：① 用 `shell: true`；② **拿手跑结果做交叉对照**（同一条命令手工跑 13/13 才能确认装置坏了而不是代码坏了）。

**通用纪律（与 §4.7 硬规则 7、§4.8 判据三条并列）**：
1. **补丁/变异必须断言落点**（哪个函数、哪一行），不能只断言"找到了"；
2. **读数前先确认识别装置可用**：拿一个**已知答案**的样本跑同一套装置（正校准），再跑待测样本；
3. **装置报出的"差异"先怀疑装置**，再怀疑被测物（本批已出现 10+ 次"我的检查工具错了"）；
4. **负向校准的红必须"红在正确的地方"**（`t62` 的 P2 红在「实盘仍以交易所为准」这条 —— 那正是它该守的）。
