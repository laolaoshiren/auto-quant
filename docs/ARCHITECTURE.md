# 架构说明

本文档面向要继续开发这个系统的人。它说明**为什么这样设计**，而不只是有什么模块。

## 2. 为什么是 TypeScript / Node

原项目 NOFX 是 Go + React。本项目选择 Node 22 + TypeScript，原因是部署环境只保证有 Node：

- **`node:sqlite`（内置）** 让持久化零依赖、零原生编译，`npm install` 不会因为
  `better-sqlite3` 之类的原生模块编译失败而卡住。
- 前后端共用 `@aq/shared` 里的 **zod schema**，`StrategyConfig` 只定义一次，
  控制台校验与后端解析用的是同一份代码，不会漂移。
- 服务端用 `tsx` 直接运行 TypeScript，省掉一整套构建顺序/产物路径问题。

## 3. 数据模型

SQLite，迁移由 `PRAGMA user_version` 管理（`src/db/schema.ts`）。

| 表 | 作用 | 关键点 |
| --- | --- | --- |
| `users` | 账户 | 首个注册者成为 owner |
| `exchange_accounts` | 交易所凭据 | `api_secret_enc` 为 AES-256-GCM 密文，**永不返回给前端** |
| `ai_models` | LLM 端点 | 同理，Key 加密存储 |
| `strategies` | 策略 | `config_json` 存完整 `StrategyConfig`；读取时**重新过一遍 zod schema**，因此升级新增字段后老策略依然可用 |
| `traders` | 机器人 | (凭据, 模型, 策略) 三元组 + 周期；`last_cycle_number` 保证审计编号跨重启连续 |
| `positions` | 持仓 | 部分唯一索引保证**每标的至多一个 open 仓位** |
| `orders` | 订单 | 含被拒绝的订单与 `raw_response` |
| `trades` | 已平仓回合 | 含 `close_reason`（模型决策 / 止损 / 止盈 / 回撤守卫 / 爆仓） |
| `decision_records` | 决策审计 | 完整 system/user 提示词、思维链、原始响应、逐条执行结果；自动保留最近 500 条 |
| `equity_snapshots` | 权益曲线 | 用于回撤与高水位计算 |
| `trade_events` | 节流记账 | 开/平仓事件，重启后节流限制依然有效 |
| `runtime_logs` | 控制台日志 | 滚动保留最近 500 条 |

**凭据加密**：`v1:<iv>:<authTag>:<ciphertext>` 自描述格式，AES-256-GCM。
主密钥优先取 `MASTER_KEY` 环境变量，否则首次启动生成 `data/.master.key`（权限 0600）。

## 4. 交易所连接层（`src/binance/`）

### 4.1 端点路由（`endpoints.ts`）

币安把合约 WebSocket 拆成了流量类别路由：

| 路由 | 内容 |
| --- | --- |
| `/public` | 高频公开数据：`depth`、`bookTicker` |
| `/market` | 常规行情：`kline`、`markPrice`、`aggTrade`、`ticker` |
| `/private` | 用户数据流（listenKey） |

**旧的无路由路径（`wss://fstream.binance.com/ws/...`）已停用。**
`stream → route` 映射表是显式的，因为路由错误的表现是
**握手成功但永远收不到任何数据** —— 这类静默失败最难排查。

### 4.2 REST 传输（`rest.ts`）

- HMAC-SHA256 签名，`signature` 必须**最后**追加，签的是实际传输的那个串。
- **启动时强制时钟同步**（`/fapi/v1/time`）。签名时间戳超出 `recvWindow`
  会被拒（`-1021` 网关层，`-5028` 撮合引擎层，两者都要重同步重试）。
- **权重预算从 `exchangeInfo.rateLimits` 读取**：实盘 2400/min，测试网 6000/min。
  硬编码测试网的值打到实盘会从 429 升级成 IP 封禁。
- 区分错误类别：时间戳错误 → 重同步后重试；限流 → 尊重退避；
  过滤器/标的/保证金错误是确定性的，**不重试**（浪费权重且无意义）。

### 4.3 WebSocket（`ws.ts`）

`ResilientStream` 处理四件真正会让长连接崩掉的事：

1. **静默僵尸连接** —— 按键流记录 `lastMessageAt`，看门狗发现超时即强制重连。
   协议层 `OPEN` 不能证明有数据。
2. **24 小时连接上限** —— 在 23 小时主动轮换，而不是等着被踢（可能正在下单中途）。
3. **退避过早重置** —— 只有**收到真实数据**才重置重试计数；若在握手成功时就重置，
   一个永远收不到数据的错误路由会造成紧密重连风暴。
4. **连接重叠** —— 新连接建立前先彻底拆除旧 socket（带超时），避免事件重复计数。

`listenKey`：创建/续期/关闭三个端点只带 API Key 头、**不签名**；
每 30 分钟续期一次（有效期 60 分钟，留一个完整重试周期）；
收到 `listenKeyExpired` 视为**强制重连 + 状态对账**信号。

**用户数据流在生产中接入了，但只用于告警。** `TraderManager` 会在机器人启动成功后
订阅用户数据流，用于 `MARGIN_CALL` 爆仓预警、订单终态日志、listenKey 失效与重连提示。
它**不下任何交易决策** —— 所有仓位状态仍然由每个周期的 REST 对账推导。
这个刻意的分离意味着：即使 WebSocket 掉线或被错误路由，
机器人的状态也不会静默失真，最多只是通知延迟。
对"必须无人值守运行"的系统来说，这样才能安全地引入一个流式依赖。

### 4.4 订单（`broker.ts`）

这是最需要小心的一个文件。

**条件单必须走 Algo Order API。** `/fapi/v1/order` 对
`STOP_MARKET` / `TAKE_PROFIT_MARKET` / `STOP` / `TAKE_PROFIT` / `TRAILING_STOP_MARKET`
一律返回 `-4120`。搞错的后果不是报错，而是**开完仓止损根本没挂上**。

两种订单的身份空间不同：

| | 普通单 | Algo 单 |
| --- | --- | --- |
| 端点 | `/fapi/v1/order` | `/fapi/v1/algoOrder` |
| ID | `orderId` / `clientOrderId` | `algoId` / `clientAlgoId` |
| 状态 | `status` | `algoStatus` |
| 触发价参数 | —— | `triggerPrice`（响应里才叫 `stopPrice`） |

broker 把两者归一化成统一的 `PlacedOrder`，交易循环因此完全不必分支。
`algoId` 是**逐标的自增**的，只在 (标的, algoId) 组合下唯一。

**撤单必须两边都撤**：`DELETE /fapi/v1/allOpenOrders` **不会**动 Algo 单，
需要额外的 `DELETE /fapi/v1/algoOpenOrders`。
`closePosition=true` 的条件单在手动平仓后依然存活，会朝反方向开出新仓 ——
所以任何手动平仓前先撤该标的的全部挂单。

## 5. 策略引擎（`src/strategy/`）

### 5.1 选币（`coins.ts`）

四种模式：`static` / `coinpool` / `oi_top` / `mixed`。

`coinpool` 与 `oi_top` 在本实现中由**币安公开数据**驱动，不依赖付费数据源：
流动性/动量筛选来自全市场 24h ticker，持仓量增长来自 `openInterestHist`。

`mixed` 模式下，被多个来源同时选中的标会**保留全部来源标签**并在提示词里
渲染为 `(coinpool + oi_top — multi-source signal)` —— 多源共振本身就是信号。

**持仓标的永远在候选集内**，即使它已经掉出了所有筛选条件：模型必须能看到并管理它手里的仓位。

### 5.2 提示词（`prompt.ts`）

系统提示词 8 段：角色 / 模式 / **硬约束** / 频率 / 入场标准 / 决策流程 / **输出格式** / 自定义。
其中硬约束段是从 `RiskControlConfig` **动态生成**的，所以控制台里改限制，
模型立刻就能看到新的边界 —— 但真正的执行者始终是风控引擎，不是这段文字。

用户提示词包含：系统状态、BTC 概览、账户、近期成交、当前持仓、候选币全量数据、
（可选）主动买卖流、持仓量排行。

**蜡烛数与渲染点数分离**：指标在完整蜡烛集上计算以满足预热
（MACD(26,9) 需要 35 根才有第一个直方图值，EMA50 需要 50 根），
但只向模型渲染最近 30 个点。默认 `primaryCount` 因此是 **60** 而不是直觉上的 30 ——
用 30 会让 MACD 静默变空。提示词体积与候选数量近似线性，
可通过 `coinPoolLimit` / `selectedTimeframes` / `primaryCount` 调节。

### 5.3 解析（`parser.ts`）

对**结构宽容**、对**语义严格**：格式烂的响应产出的结果是"没有决策"，而不是"畸形订单"。

- 思维链提取：`<reasoning>` → `<decision>` 之前的文本 → JSON 之前的文本 → 全文。
- JSON 提取：`<decision>` 内代码块 → 内裸数组 → 任意代码块 → **括号配平扫描**。
  用 `indexOf(']')` 会在字符串里出现 `]` 时截断。
- 编码修复：中文引号/全角括号/冒号 → ASCII；剥离零宽字符；修尾随逗号。
- 字段别名：`size`/`sl`/`tp`/`conf`/`lev` 等模型常用简写都能识别。
- 校验：action 合法性、标的是否在候选集内、平仓方向是否与持仓一致、
  是否重复开仓。**未知 action 会作为"被拒绝"上报并附理由**，而不是静默丢弃。

## 6. 风控引擎（`src/risk/engine.ts`）

设计上的核心：**模型提议，运行时裁决**。模型输出被当作不可信输入。

### 审查顺序

1. 账户权益 > 0
2. 标的有可用价格（绝不在没有价格的情况下盲目下单）
3. 持仓槽位未满
4. 置信度达标
5. **杠杆钳制**（BTC/ETH 与山寨币分别设限，取模型值与上限的较小值）
6. 止损存在（缺省则按配置的兜底百分比推算）
7. 止盈存在（同上）
8. 保护价位必须在正确一侧（多头止损低于现价等）
9. 盈亏比达标
10. 名义价值上限（按权益倍数）
11. 保证金预算（同时受 `maxMarginUsage` 与可用余额约束，超了就缩减名义价值）
12. 最小下单量（交易所 `MIN_NOTIONAL` 与配置值的较大者）
13. 节流（每轮/每小时开仓次数）
14. 数量可按交易所步长取整（取不到整数手就直接拒绝）

**同批次内的开仓会互相看到对方的保证金消耗** —— 否则一批里的多个开仓
可以合起来突破账户上限。

**平仓几乎没有限制**（仅最小持仓时间）：减少风险敞口永远是安全方向，
"拒绝平仓"是把小亏变成爆仓的经典方式。

### 兜底钳制的方向性

`clampStopLoss` 与 `clampTakeProfit` 是镜像的两个函数。
把两者合并成一个"把价格钳到入场价安全侧"的函数，会**静默地让每一笔交易的止盈都失效** ——
这个 bug 在开发期被单元测试抓到过一次。

### 回撤守卫与熔断器

- **回撤守卫**：浮盈超过激活阈值后，若从峰值回吐超过设定比例则自动平仓。
  这是机械规则，跑在问模型之前，因为"保护已有利润"恰恰是模型最不可靠的判断。
- **熔断器**：单日已实现亏损上限、总回撤上限（相对权益高水位）。
  只阻止**新开仓**，不平掉已有仓位（那是回撤守卫的职责）。
- **安全模式**：连续失败达到阈值后，在模型恢复前禁止新开仓。

## 7. 交易循环（`src/trader/`）

### 周期不重叠

`cycleInFlight` 守卫：跑超时的周期不会被下一个 tick 覆盖执行 ——
那会导致仓位重复计数与订单重复提交。

### 对账（`reconcilePositions`）

仓位可能在我们完全没收到 WebSocket 事件的情况下消失：交易所侧止损/止盈触发，或爆仓。

- **本地有、交易所有** → 继续持有，并**上抬该仓位的浮盈峰值**（回撤守卫要用）。
- **本地有、交易所没有** → 判定平仓原因并记账。判定方式是查
  `openAlgoOrders`：我们的止损/止盈不再挂着、而仓位也没了，说明它触发了。
  这比匹配成交记录可靠 —— 触发的 Algo 单会生成一个我们事先不可能知道的
  `actualOrderId`。
- **交易所有、本地没有** → **收养**。手动开的仓位不能被无视，否则模型会在错误前提下决策。

### 止损挂不上时的处理

开仓后先挂止损并**验证**。若止损挂不上且配置要求必须有止损，
则**立即市价平仓**，并记录一条明确的错误。
一个没有保护的杠杆仓位是最糟糕的状态，宁可立刻退出。

### 生命周期（`manager.ts`）

每个机器人拥有独立的交易所连接、行情缓存与模型客户端 ——
一个机器人的限流压力或某个 LLM 提供商故障不会影响另一个的决策。

启动前预检（preflight）：凭据存在 → 账户可读 → 余额非零 →
API Key 有合约交易权限 → 仓位模式（单向/双向）→ 合约元数据已加载 → 时钟偏移 →
模型端点可达。任何**阻塞性**失败都会拒绝启动并给出明确原因。

服务器重启后会**恢复**之前处于 `running` / `safe_mode` 的机器人。

## 8. LLM 层（`src/llm/`）

提供商无关。`LLM_PROVIDERS`（`@aq/shared`）描述每个提供商的
base URL、鉴权方式、推荐模型、是否兼容 OpenAI 方言、JSON 模式能力。

已逐个吸收的厂商怪癖：

- **Anthropic**：`system` 是顶层字段而非消息；响应 `content` 是块数组，
  必须只拼接 `type === 'text'` 的块；当前模型拒绝 `temperature`。
- **Gemini**：完全不同的 REST 形状，角色是 `model` 而非 `assistant`，
  结构化输出用全大写 schema 类型。
- **MiniMax**：**在 HTTP 200 里返回错误**（`base_resp`），必须识别并抛出。
- **Kimi**：拒绝 `temperature`/`top_p`/惩罚项。
- **OpenRouter**：严格 schema 的遵守程度取决于上游提供商。

所有提供商统一：指数退避 + **全抖动**（避免共享故障后的重连风暴）、
`AbortSignal.timeout` 超时、只对可重试错误重试、**永不记录 API Key**。

## 9. 扩展指引

### 新增交易所

1. 在 `@aq/shared` 的 `ExchangeIdSchema` 加入新 id，并在 `EXCHANGES` 描述。
2. 实现等价于 `src/binance/` 的连接层，满足 broker 的语义契约：
   `getAccountState` / `getPositions` / `setLeverage` / `placeOrder`（返回归一化 `PlacedOrder`）/
   `waitForFill` / `cancelAllOrders` / `getUserTrades` / `getMarkPrice`。
3. 在 `TraderManager.connectionFor` 里按 `exchange` 字段分派。
4. 注意**条件单语义差异**：止损在有些交易所是普通单类型，有些是独立端点。

### 新增 LLM 提供商

若兼容 OpenAI 方言，只需在 `LLM_PROVIDERS` 加一条（`openAiCompatible: true`）。
否则仿照 `src/llm/anthropic.ts` 实现适配器，并导出可测的
`buildBody` / `parseResponse` 纯函数。

### 新增风控规则

在 `RiskEngine.reviewOpen` 里加检查，并在 `Decision.adjustments` 里
写清调整原因 —— **每一次运行时对模型的推翻都必须留下痕迹**，
这是这个产品可被信任的前提。

## 10. 测试

```bash
npm test                                     # 全部后端测试
npx tsx --test src/risk/engine.test.ts       # 风控引擎（27 个用例）
npx tsx --test src/strategy/parser.test.ts   # 响应解析（27 个用例）
npx tsx --test src/market/indicators.test.ts # 技术指标（16 个用例）

```

指标测试里固化了经典参考值（Wilder RSI、EMA），
风控测试覆盖了每一条限制与钳制方向 —— 这是防止"看起来对但方向反了"这类
静默错误的主要防线。
