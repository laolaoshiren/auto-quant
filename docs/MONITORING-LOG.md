### 发现 2 · 熔断警告每个周期重复两条 ⚠️ **（BUG，已定位）**

一小时 920 条日志，其中：

```
× 21  单日亏损熔断：今日已实现亏损 $0.59，占权益 6.03%（上限 5%）。
× 21  [测试2] 单日亏损熔断：今日已实现亏损 $0.59，占权益 6.03%（上限 5%）。
```

**根因（读代码确认）**：`autoTrader.emit()` 的一次调用产生**两条库记录 + 两个前端事件**，
因为同一个消息走了两条落盘路径：

```ts
// autoTrader.ts:307
private emit(level, message): void {
  log[level](`[${trader.name}] ${message}`);           // ① → 触发全局 sink
  runtimeLogs.write(trader.id, level, 'trader', message);  // ② → 直接写库
  eventBus.publish({ type: 'log', ... });              // ③ → 直接推前端
}

// server.ts:1616 —— 全局 sink（①②两条路径最终都到这里）
setLogSink((level, scope, message) => {
  runtimeLogs.write(null, level, scope, message);      // trader_id = NULL
  eventBus.publish({ type: 'log', traderId: null, message: `[${scope}] ${message}` });
});
```

于是**同一个事件**变成：
- 一条 `trader_id = NULL`、带 `[测试2]` 前缀（服务器日志视图）
- 一条 `trader_id = 5`、不带前缀（机器人日志视图）
- 两个 WebSocket `log` 事件 → 界面上同一件事出现两次

**影响**：约 42/920 条，是**日志噪音**而非资金问题。但它确实让同一件事在界面上重复，
而且 `log[level]` 走 sink 的那条**丢了机器人归属**（`trader_id = NULL`），
所以按机器人筛选日志时会漏看它。

**不修的原因**：`autoTrader.ts` 正被另一个代理编辑（陈旧委托修复）。
**等它完成后处理**，避免制造冲突。

### 发现 7 · 熔断生效时仍在花钱调用模型 ⚠️ **（浪费，已定位，待修）**

代码顺序（`autoTrader.ts`）：

```
L651  const breaker = checkCircuitBreakers(...)    ← 检查熔断
L655  if (breaker.blocked) this.emit('warn', ...)   ← 只记日志
L713  buildSystemPrompt(...)                        ← 构建 58k token 提示词
L725  await this.deps.model.complete(...)           ← ★ 花钱调用模型
L796  if (breaker.blocked) { ... }                  ← ★ 到这里才真正拦截
```

**熔断在 L651 检查，却在 L796 才执行——中间隔着一次完整的模型调用。**

每个周期都在做：构建 5.8 万 token 提示词 → 付费请求模型 → **把全部决策丢掉**。

实测损失：熔断生效 + 持仓 0 → 每轮 58,266 输入 + 约 9,000 输出
→ **约 134 万 tokens/小时，产出为零**。熔断按"单日"计算，可能持续数小时。

**修法（不是简单地"熔断就跳过模型"）**：

熔断**只拦新开仓，不拦平仓**。有持仓时模型必须继续跑（决策里可能有平仓）。
**只有「熔断生效 且 无任何持仓可管理」时跳过模型调用才安全**——此时模型
不可能产出任何可执行的东西。

跳过时要**照常写一条决策记录**说明原因，否则操作者会以为机器人卡住了。

**待修原因**：`autoTrader.ts` 正被另一个代理编辑。等它完成立即处理。

## 轮次 4 · 2026-09-16 22:05（第 75 分钟）

### ✅ 已修复：日志双写（同一句话出现两遍）

**根因**：`AutoTrader.emit()` 与全局 log sink **各写一次库、各推一次事件**。

```
① log[level]('[测试2] …')  →  全局 sink  →  写库(trader_id=NULL) + 推事件
② runtimeLogs.write(5, …)  →  又写一条
③ eventBus.publish(…)      →  又推一次
```

**修法不是删掉一条**（那会丢机器人归属），而是**让 sink 感知归属**：
`emit()` 把 `{ traderId, raw }` 通过 `meta` 交给 sink，由 sink 统一落盘与推送。
于是 `trader_id` 保住、记录只剩一条、事件只推一次。

实测：机器人日志 35 条，**同毫秒重复 0 处**。

### ✅ 已修复：状态型警告每周期都写

熔断与候选池裁剪**每个周期都会再次成立**，却按事件每轮写一次 —— 一小时 21 条
同一句话，真正的异常被埋掉。**一个每轮都响的警告等于没有警告。**

新增 `emitOnChange(key, level, message)`：状态没变就不再记；**解除时记一条"已解除"**
再清状态，这样"什么时候开始的、什么时候结束的"两个时刻都有记录。
候选池裁剪同理（按文案去重，数字变了会重新记）。

实测（4 个周期的窗口）：

| 日志 | 修复前 | 修复后 |
| --- | --- | --- |
| 单日亏损熔断 | 每轮 2 条 | **只记 1 条（进入时）** |
| 候选池裁剪 | 每轮 1 条 | **0 条** |

### ⚠️ 我在测量时犯了一个错

第一次统计日志速率时用了 `created_at >= datetime('now','-8 minutes')`，
但库里存的是 **ISO 格式**（`2026-09-16T13:52:28.301Z`，带 T 和 Z），
而 `datetime()` 产生的是**空格分隔**格式 —— **字符串比较全部为真**，
于是我读到"8 分钟新增 769 条"这种明显不可能的数字。

改用 `new Date(...).toISOString()` 比对后得到正确结果。
**教训：时间戳跨格式比较前先确认两边的格式一致**，否则会得出任意结论。

**根因**：`connect()` 第一步 `await this.teardown()` 关掉上一个 socket（code 1000），
而**那个 socket 的 close 处理器仍然挂着**，于是它触发"干净关闭 → 立刻重连"，
新的 `connect()` 又关掉刚建的 —— 循环。

**实测：10 分钟 76 次 `clean-close` + 33 次 `close 1006`。**

修法：三个处理器都先判 `this.socket !== socket`，不是当前 socket 的事件就忽略。
**守卫不破坏 teardown** —— 它先置空再关闭，并用自己的 `once('close')` 等待终止。

修复后：`clean-close` **0**、`close 1000` **0**、`close 1006` **0**。

### 发现 9 · 运行期的平仓**原因**被对账覆盖成"对账补录" ⚠️

**现象**：三笔在机器人**运行中**发生的平仓，由对账补录，且原因是 `对账补录`
而不是 `触发止损` / `触发止盈`：

```
#25 POWERUSDT 空 201  0.118927→0.119713  净 -0.1821  reconciled
#24 SYNUSDT   多  72  0.1916→0.1966      净 +0.3460  reconciled
#23 LSKUSDT   多  23  0.63862→0.63033    净 -0.2053  reconciled
```

日志原文说「平仓发生在机器人未运行时」——**但机器人一直在跑**，那句话是补录路径的
**假设**，不是事实。

**先确认这是设计选择，不是故障**：

```ts
// manager.ts:134
onOrderUpdate: (event) => {
  // Only surface the transitions an operator cares about;
  // the REST loop remains the source of truth for fills.
  if (o.X === 'FILLED' || ...) emit('info', `订单 ...`);
},
```

**WebSocket 只用于提示，不记账** —— 记账交给 REST 对账。**账目最终是正确的**
（日志写明「已从交易所成交记录恢复」），这一点没有问题。

**真正的问题在顺序**：

```
L673  await this.reconcileTradeHistory(false)   ← 先跑：从交易所成交历史重建
L678  await this.reconcilePositions(...)        ← 后跑：从"仓位消失"推断真实原因
```

止损在交易所触发 → 下一个周期 `reconcileTradeHistory` **先**发现这笔未记账的回合，
按 `reconciled` 记下 → 等 `reconcilePositions` 再跑时已经无事可做 →
**真实的平仓原因永远没被确定**。

**为什么这不只是"标签不好看"**：

- `对账补录` 是所有标签里信息最少的一个；操作者看不出这笔是怎么结束的；
- **模型的「最近平仓」区块看到的是 `对账补录` 而不是 `触发止损`** ——
  而那个区块存在的意义正是让模型把"我当时的理由"和"实际结果"对上。
  标签错了，学习信号就被削弱。

**推测的修法**：`reconcilePositions` 先跑（它能用 `detectCloseReason` 定出真实原因），
`reconcileTradeHistory` 只兜底剩下的（进程离线期间发生的平仓）。

**为什么这一轮没有直接改**：重排对账顺序正是那种会导致**重复记账或漏记**的改动，
需要专门一轮来做并配套测试。**不能顺手改。**
