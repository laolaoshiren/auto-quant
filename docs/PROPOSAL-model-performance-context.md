# 方案：让模型看见自己的绩效

**状态：待评审，未实现。**

---

## 1. 诊断：问题不在方向判断

操作者用 3 分钟周期测试后报告「频繁开仓/平仓导致亏损」。实测数据支持这个判断，
而且**指向的根因比"太频繁"更具体**：

```
15 笔成交
  毛盈亏:   -0.0294 USDT      ← 扣费前的方向判断，基本是随机的
  手续费:    0.2894 USDT      ← 10 倍于毛盈亏
  净:       -0.3189 USDT

平均持仓: 4.3 分钟
单笔往返成本: 名义价值的 0.1000%
```

**手续费 / |毛盈亏| = 983%。**

这个账户在扣费前接近持平。**它亏的钱全部是手续费。**

结论：**问题的性质不是"模型的判断不准"，而是"它在做一件数学上不成立的事"** ——
每次出手先付出 0.1%，而单笔毛盈亏的中位数还不到这个数。频率放大只会放大这个差额。

### 为什么模型会这样

它**不知道自己在亏**。每一轮它看到的是干净的行情、干净的账户、没有持仓——
从它的视角，每一轮都是全新的、值得评估的机会。

它看不到：

- 它刚刚在 4 分钟前平掉了一笔，亏了手续费
- 它今天已经开了 7 笔，累计手续费 0.29
- 它连续用了同一个理由（"1M 突破"）在同一个标的上反复进出

## 2. 要加入提示词的东西

**原则：加「聚合统计」而不是「历史明细」。** 聚合在提示词里是 **O(1) 大小**，
明细是 O(n)。这是这一节最重要的工程判断。

### 2.1 交易绩效区块（固定约 200 tokens，永远不增长）

```
# 你的交易绩效
最近 24 小时：7 笔（2 胜 5 负）· 毛 -0.03 · 手续费 -0.29 · 净 -0.32
平均盈利 +0.15 · 平均亏损 -0.18 · 实际盈亏比 0.83（要求 ≥ 1.5）
每次往返成本约 0.10%（名义价值）
**手续费是毛盈亏的 9.8 倍 —— 减少交易次数是当前唯一有效的改进方向。**
```

最后那一行是**反过度交易的核心信号**。它把"你在亏"直接翻译成"你该少做"，
而不是让模型自己从一堆数字里推断。行内的倍数由服务端计算，**不是固定文案**。

### 2.2 最近平仓（固定 N=5 笔，每笔两行）

```
# 最近平仓
- SYNUSDT 多 5x @0.18050→0.18020  净 -0.048  触发止盈  (3 分钟前)
  你当时的理由：1M 放量刷新低点，RSI7 12 超卖
```

**第二行是关键**——把模型**当时的理由**和**实际结果**放在一起。这是唯一能让它
形成"我的某个判断模式不奏效"的机制。没有这一行，明细只是流水账。

`N` 固定为 5，所以大小恒定。

### 2.3 行为余量（让模型知道自己离约束多远）

```
# 本周期约束
本小时已开仓 2 / 3 笔 · 上次平仓在 4 分钟前（再入场冷却 15 分钟，还剩 11 分钟）
```

这些约束**现在已经在代码里强制执行**，但模型看不见。看不见的约束等于不存在——
它会反复提出会被拒绝的请求，浪费调用，也浪费一次决策机会。

### 2.4 明确不要加的

| 不加 | 理由 |
| --- | --- |
| 完整成交历史 | O(n) 增长，7×24 跑一年后提示词会爆 |
| 更多 K 线 / 更多指标 | 现在已经是提示词的主体，再加会挤掉上面这些 |
| 逐笔的完整推理全文 | 只带上"当时的一句话理由"，不要全文 |

## 3. 上下文预算：必须有一个硬上限

现在提示词已经约 **20,000 tokens**，其中**每个候选标的约 6,700 tokens**。

加入上面三块（约 **400 tokens**）相对可以忽略。但**必须同时加一个预算守卫**：

> 组装完成后估算 token 数（`estimateTokens()` 已存在）。**超过上限时，
> 优先裁剪「候选标的」——从最弱的开始丢。绩效与历史区块不裁。**

**这个取舍方向是刻意的**：预算紧张时**砍行情数据，不砍记忆**。

理由：行情数据是"这一轮的机会"，记忆是"我一直在亏钱"。
丢掉前者只是错过一次机会，丢掉后者会让系统**永远重复同一个错误**——
而后者正是当前问题的根源。

## 4. 7×24 长期运行会怎样

这是必须回答的问题，因为任何随时间增长的东西最终都会坏掉。

| 区块 | 增长性 | 一年后 |
| --- | --- | --- |
| 交易绩效 | **O(1)** —— SQL 聚合，按时间窗口 | 不变 |
| 最近平仓 | **O(1)** —— 固定 N 笔 | 不变 |
| 行为余量 | **O(1)** —— 计数与时间差 | 不变 |
| **提示词总大小** | **O(1)** | **不变** |

**关键设计：所有随时间累积的量都在 SQL 里聚合，进提示词的只有聚合结果。**

这带来一个可测试的硬性质：

> **机器人跑满一年后，单轮提示词的 token 数与第一天相同（±5%）。**

这条要写成测试（构造大量历史记录，断言提示词大小不随记录数增长）。
**没有这条保证，"7×24 运行"就只是一个说法。**

### 需要保留的精简历史（可选，第二期）

长期看还有一类信息值得保留：**"我在什么市况下反复亏钱"**。
但它的正确形态是**周期性滚动的汇总行**（例如每天一行、保留 30 行），
不是原始明细。这条**建议放到第二期**，因为它的收益需要更多样本才能验证。

## 5. 风控层：手续费感知的入场门槛

上面都是"让模型知道"。但**知道不等于会改**，所以还需要一条**硬约束**。

现有风控有 `minRiskRewardRatio`（要求盈亏比）。它有个漏洞：

> **一笔盈亏比达标但仍然必亏的交易。**
> 如果止损距离小于往返手续费，那么这笔交易"做对了"也是亏的。

建议新增一条校验：

```
止损距离（|开仓价 − 止损价| / 开仓价）必须 ≥ 往返手续费 × K
```

`K` 建议从 **3** 起步（即止损幅度至少是手续费的 3 倍），可配置。
理由是：止损幅度等于手续费时，胜率再高也只是在给交易所打工。

**这条规则会拒绝掉一批"看起来没问题"的交易**，而那正是目的——
它把"手续费"从模型的一个考虑项，变成一条**代码强制执行的边界**（§2.1：
风控是通往订单的唯一路径）。每次拒绝都要写进 `reason` 并带具体数字。

## 6. 分期建议

| 期 | 内容 | 预期效果 |
| --- | --- | --- |
| **一期（建议先做）** | §2 的三块提示词 + §3 预算守卫 + §4 的 O(1) 测试 | 让模型看见自己在亏，**这是最直接的止血** |
| **二期** | §5 手续费感知的风控门槛 | 硬约束兜底，即使模型不改也有边界 |
| **三期** | §4 的滚动汇总（市况记忆） | 需要更多样本才有意义 |

**一期和二期都有独立的止血价值**，不依赖对方。

## 7. 未验证 / 需要说明的

- **我没有实测**加入这些区块后模型的交易频率是否真的下降。这需要在一期完成后，
  用**同样 3 分钟周期跑同样的时长**做对照——而且对照组必须是"同一段行情"，
  否则行情本身的变化会掩盖效果。**严格说，这只能通过模拟盘对照实验来验证**，
  我建议用 `npm run sim:live`（真实模型 + 模拟交易所）做，不动真钱。
- 手续费率我用的是**实测平均值 0.1000%**（15 笔的均值）。不同标的、
  不同 VIP 等级会不同，所以**代码里不应写死**，要么从成交记录实时算，
  要么做成配置项。
- `K = 3` 是我的判断，不是实测结论。**它偏保守，可能需要按实际胜率调整。**
- 那 15 笔样本里**有 3 笔是重复记账的**（另一个代理正在修）。它不影响本节结论
  （手续费是真实发生的），但会让"该做多少笔"的统计略微失真。
