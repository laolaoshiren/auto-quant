# 缓存命中调研：4.8% 是真实数字，但它不是「可以修好的低效」

## 结论速览

| 问题 | 答案 |
| --- | --- |
| 缓存命中率是多少？ | **4.8%**（实测生产记录，非估算） |
| 这是不是花费高的主因？ | **不是主因，但确实是浪费** —— 输入占成本 81%，其中未命中部分占绝大多数 |
| 能不能「优化命中率」省很多钱？ | **不能** —— 重排提示词让恒定文本前置，**每月只省 $2（1.6%）** |
| DSH 那边为什么能 99.5%？ | **因为它是多轮对话**，与本项目的「每轮独立决策」不是同一件事 |
| 真正的省钱途径？ | **减少每轮发送的数据量**（省 41%）或**减少轮次**（省 50%） |

---

## 一、4.8% 是怎么来的，为什么不是 99.6%

### 我一开始测错了

第一版测量用的是**已经跑过的历史提示词**，测出 99.6% —— **那个数字是假的**。
那些提示词早就在服务端缓存里了（因为之前跑过同样的请求），**再发一次当然命中**。

**直到生产开始写入真实数据，才看到真相：**

```
周期 #658  prompt=50261  cached=2432  → 4.8%
周期 #659  prompt=50246  cached=2432  → 4.8%
```

### 分叉点在第 25 个字符

```
系统提示词  4675 字符   两轮完全相同  → 命中 2432 tokens ✅
用户提示词 69653 字符   公共前缀 25 字符 → 其余 69628 字符全部失效 ❌
```

两个相邻周期的用户提示词：

```
#" 系统状态\n时间：2026-09-18T18:33:54.358Z（UTC）\n机器人：..."
 ↑ 第 25 个字符是时间戳，从这一位开始就不一样了
```

`2432 / 50254 = 4.8%` —— **与实测完全吻合。命中的就是系统提示词那一块。**

### DeepSeek 的缓存规则

官方文档（Context Caching）：**前缀匹配，以 128 token 为一块**。

**前缀一旦分叉，后面再相同也不命中。** 所以「时间戳排在第一行」这一件事，
就让后面 69,628 个字符的**全部重复内容**（那 7 个候选标的的 K 线序列、
规则文本、任务说明）**一个 token 都没用上**。

---

## 二、为什么「重排提示词」救不了它

一个自然的想法：把**恒定不变**的内容挪到最前面，让缓存能多命中一段。

**算过了，收益是 $2/月。**

| 方案 | 每月 | 省 |
| --- | --- | --- |
| 现状 | $127 | — |
| **把恒定文本提到最前** | **$125** | **$2（1.6%）** |
| 每轮数据减半（`promptPoints` 30→15） | $75 | **$52** |
| 候选标的 7→4 | $83 | **$44** |
| 决策周期 3→6 分钟 | $64 | **$64** |

**原因**：这个提示词里能称得上「恒定」的只有任务说明与段落标题，**约 1200 字符**。
**其余 97% 是每轮必变的实时数据** —— 价格、指标序列、持仓、绩效、资金费。

**交易机器人的提示词，本质上是「一屏实时行情 + 一句你该怎么办」。**
行情每轮都变，所以缓存命中率有硬上限，而且那个上限很低。

---

## 三、DSH 为什么能 99.5%：它是**多轮对话**

这不是实现水平的差距，是**两种用法**：

| | DSH | 本项目 |
| --- | --- | --- |
| 每轮请求 | 在**上一轮上下文后追加** | `[system, user]` **独立请求** |
| 前缀 | 逐轮累积，越来越长 | 每轮重写，第 25 字符就分叉 |
| 命中率 | **趋近 100%**（历史全在缓存里） | **上限很低**（只有共用的 system） |

代码上就是这一句（`llm/client.ts`）：

```ts
async complete(systemPrompt: string, userPrompt: string) {
  return this.chat([
    { role: 'system', content: systemPrompt },
    { role: 'user', content: userPrompt },   // ← 每轮全新
  ]);
}
```

**所以「DSH 能做到 99.5%，项目为什么不能」的答案是：**
**项目在做一件不同的事** —— 每轮让模型**重新、独立地**看一遍市场。

---

## 四、如果改成多轮对话会怎样

**理论上很划算**：第 N 轮只需为新增的 ~200 token 付未命中价，
历史全部命中。输入成本从 `$0.0072/轮` 降到约 `$0.0015/轮`。

**但这个换法有三个真问题，所以我没有做：**

1. **上下文会滚雪球**：每轮 50K，10 轮就 500K，100 轮就 5M（超过 1M 上限）
2. **语义会变**：模型会锚定在自己之前的判断上，而现在的设计是
   「每轮重新判断一次」—— **那是这个机器人的一条核心性质，不是实现细节**
3. **首次未命中会非常贵**：上下文越长，一次冷启动越贵

**这是一条产品决策，不是技术优化。** 需要的话可以做成开关。

---

## 五、真正的省钱途径（按性价比排序）

| 手段 | 每月 | 省 | 代价 |
| --- | --- | --- | --- |
| **决策周期 3→6 分钟** | $64 | 50% | 反应变慢 |
| **`promptPoints` 30→15** | $75 | 41% | 模型看到的 K 线变短 |
| **候选标的 7→4** | $83 | 35% | 可选机会变少 |
| `reasoning_effort` high→low | 约 $100 | 约 20% | 思考变少 |
| 重排提示词提高命中 | $125 | **1.6%** | **不值得做** |

**前三项都是「用判断质量换钱」，取舍该由机器人主人决定，不该由代码替他决定。**

---

## 六、已经做的改动（让这件事以后不用再靠猜）

数据库里现在会记录每一轮的 `cached_tokens` 与 `reasoning_tokens`，
「最近决策」里直接显示 `缓存 N%` 与 `思考 N%`。

**在此之前这两个字段在归一化那一步就被丢掉了**，
所以「缓存命中了多少」「钱花在思考还是正文」两个问题**都没有任何地方能看到** ——
这正是这次要靠一轮轮手工测量才能得出结论的原因。

**一个不显眼的区分**：`null` 是「服务商没上报这个字段」，
`0` 是「上报了，确实一个都没命中」。**合成 `?? 0` 会把不支持的供应商显示成
「缓存全没命中」**，而这两件事该做的事完全相反。
