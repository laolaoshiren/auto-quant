## 一、Jev 是什么（调研结论）

| 维度 | Jev | 我们团队模式现在用的 LLM |
|---|---|---|
| **输出** | **只有类型化决策**（choice / noul 是-否概率 / score），**不产生任何文字** | 自由文本 + JSON |
| **推理** | **不做**（不解释、不链式思考、不调工具） | 全套 |
| **延迟** | **70–500 ms**（官方数据） | 单次 10–60 s |
| **成本** | **$42 / 十亿 input token**，output 不计费 | 约 300 倍 |
| **幻觉** | **零**（只从你给的 options 里选，编不出新东西） | 有 |
| **上下文** | 64k（其中 state 预算 32k） | 更大 |

**实测（本地 magpie，2026-10-18）：**
```json
POST http://127.0.0.1:3425/v1/systemone
{ "state": "BTCUSDT 15m 跌幅 -1.2%，ATR 1.8%，RSI14 32…",
  "model": "jev-latest",
  "questions": { "direction": { "type": "choice",
    "instructions": "这个标的接下来更可能往哪个方向走？",
    "criteria": {"up":"看涨","down":"看跌","unclear":"看不清"} } } }

→ {"model":"jev-1.13.0",
   "answers":{"direction":{"choice":"down","confidence":0.27,
     "probabilities":{"up":0.12,"unclear":0.37,"down":0.51}}},
   "usage":{"input_tokens":386,"output_tokens":39}}
```

**注意 `confidence: 0.27`** —— 它已校准、知道自己不确定。这是它相对 LLM 的核心价值：
LLM 在被追问时会"编一个看起来自信的答案"，Jev 给的是**概率分布**，下游可以直接用阈值。

## 二、它**不能**做什么（这是最重要的判断）

❌ **不能替换分析师 / 裁决官。** 那些角色产出的是长段推理（`hypothesis`、`structure`、
`arguments`、`invalidates`），而 Jev **不产生任何文字**。让 Jev 做裁决 = 让团队失去可解释性，
而项目纪律明确要求"每一次运行时对模型的推翻都要留下痕迹"。

❌ **不能做需要跨标的比较的判断**（除你把全部候选塞进一个 state —— 但那样 state 会很大）。

❌ **不能做需要工具调用的活**（搜新闻、查链上、读历史）。

---

## 三、它**能**做什么（本次实验的切入点）

### 切入点：**逐币初筛**（pre-filter）

**现状测量（线上 #11）：**
```
每轮 ai_latency：87 / 272 / 331 / 337 / 513 / 300 / 331 / 476 秒   ← 平均 ~330 秒
每轮 tokens_in 平均：144,309
按币并行：18 个标的 × 每个一次 LLM 调用
```

**瓶颈很清楚：18 个标的**每个都要过一次 LLM**，而其中大多数会得出"不可执行"。**

**Jev 的位置：**
```
  18 个标的的市场摘要
        ↓
  【Jev score 问题】每个标的打一个"值得深看"的分（或一次 noul：这个标的今天有机会吗）
        ↓
  按分数取前 N（N = 4~6）
        ↓
  只对这 N 个跑 LLM 深度分析（现在的 per_symbol 链）
        ↓
  辩论 → 裁决 → 执行（完全不变）
```

**预期收益：**
- LLM 调用次数 18 → 5，**每轮省 ~70% 的 token 与时间**
- 决策质量：由 Jev 的概率 + 阈值控制，阈值可调
- 成本：Jev 侧几乎免费（$42/十亿 token vs LLM 的 ~$3000/十亿量级）

**预期风险（必须监控）：**
- ❗ **Jev 把有潜力的标的筛掉了** ⇒ 漏掉交易机会（这是最严重的，需对比"Jev 筛除的标的后来涨跌如何"）
- ❗ Jev 对加密行情的理解不足（它训练在通用文本上，可能不认识 `ATR`/`RSI`/`资金费率` 的含义）
- ❗ 多一个外部依赖 ⇒ 多一个故障点

## 四、接入方式（设计）

### 开关

```
AQ_JEV_PREFILTER=on      # 默认 off。off 时行为与改动前【逐字一致】
AQ_JEV_TOP_N=6           # 初筛后保留几个（默认 6）
AQ_JEV_MIN_SCORE=0.5     # 分数低于此的直接跳过
AQ_JEV_MODEL=jev-latest
AQ_JEV_BASE=http://127.0.0.1:3425   # magpie 网关
```

### 失败降级（硬要求）

**Jev 任何失败（网络、超时、格式、低置信）都必须回落到"不筛"** ——
也就是等价于 `AQ_JEV_PREFILTER=off` 的行为，**绝不因为 Jev 挂了而少看标的**。

### 观测

每个周期记录（写 `runtime_logs`，scope=`jev`）：
```
[Jev] 18 个标的 → 打分完成 · 最高 0.82 · 最低 0.11 · 保留 6 个 · 耗时 340ms
[Jev] 筛除：XRPUSDT(0.21) HYPEUSDT(0.18) …（这些标的本轮不进 LLM）
```

### 判定标准（事先定好，避免事后找理由）

**保留（正向）** 需要同时满足：
1. **LLM 调用数显著下降**（≥50%）
2. **每轮耗时下降**（中位数降 ≥30%）
3. **没有漏掉机会**：Jev 筛除的标的中，"若当时开仓会盈利"的比例 ≤ 全部候选的盈利比例
4. 10 小时内 Jev 失败次数 < 5%，且每次都能正确降级
5. 团队模式的**实际盈亏不劣于**开启前的同等窗口

**移除（负向）** 只要满足任一：
1. 筛除了后来大幅波动（>3%）的标的 ≥ 3 次
2. Jev 失败导致降级异常（漏标的、报错、卡住）
3. 盈亏明显变差
4. 维护成本 > 收益（例如 magpie 更新后反复坏）

## 六、magpie 自动更新的兼容性风险

**这是用户提出的第二个问题：**

> 「既然项目团队模式高度依赖 magpie，那么是否有些功能/设置会因为 magpie 的改动更新而需要做相应的调整，
>   如果有你得跟进，还要研究看看有没有一劳永逸的方案（不让这个成为项目包袱）」

### 现状：哪些地方依赖 magpie

| 依赖点 | 形式 | 更新后可能坏在哪 |
|---|---|---|
| `baseURL: http://127.0.0.1:3425/v1` | OpenAI 兼容协议 | 端点路径变化 |
| 模型 id（`group/*`、`opendesign/*`） | 字符串 | 提供商改名 / 模型下架 |
| `unrecognized_model` 等错误文案 | 字符串匹配 | 文案变化 → 判定失效 |
| `/v1/models` 的响应形状 | JSON 结构 | 字段改名 |
| **Jev 的 `/v1/systemone`**（本次新增） | 独立协议 | **最容易坏**：非标准端点 |

### 一劳永逸的方向（待评估）

1. **契约自检**：启动时 + 每小时探测一次 magpie 的关键契约（`/v1/models` 形状、一次最小 chat 调用、一次 Jev 调用），
   不一致就**告警而不是静默失败**。
2. **能力探测代替硬编码**：不写死模型 id，启动时从 `/v1/models` 读；找不到就明确报"该模型不在网关上"。
3. **协议适配层收口**：所有 magpie 调用集中在一个模块（`llm/gateway.ts`），端点/路径只在那里出现一次。
4. **固定 magpie 版本**（关掉自动更新）—— 但用户明确说要自动更新，所以不走这条路。
